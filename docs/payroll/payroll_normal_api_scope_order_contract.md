# Normal payroll mutation scope order — staged source contract

This independent stage follows the known signature/site/trade/vehicle scope migration. It is not applied to production. Exact original body/config/security guards precede all new DDL and reject unknown definitions, including the existing lock helper and settings refresh trigger function. The delegated professional portal writer is also guarded but its body is not replaced. Existing function signatures, client permissions, notifications, approval rules, cancellation snapshots, RLS and grants remain unchanged.

| Entry | Captured scopes before original row locks | Recheck |
| --- | --- | --- |
| Force attendance | All input worker/date tuples; old affected reports and attendance; existing destination reports and every report worker | Captured source after ordered parent locks; unexpected later destination fails 40001 |
| Correction decision | Request/items, linked attendance old tuples, proposed past-attendance tuples, linked report workers | Request row then ordered report locks, exact source recheck before mutations |
| Leave submit / retrospective | Explicit requested dates and authenticated worker/company | Worker lock serializes balance reads and inserts; original date/balance validation remains |
| Leave decision | All pending batch rows and dates, authorized tenant | First original request row lock then pending capture recheck |
| Cancellation | Existing report header, old attendance tuples, all roster workers | Report row lock then source recheck; original preview/blocked/fingerprint/audit rules remain |
| Destination draft | Explicit new roster/date plus old report/attendance/roster, including approved signed-report replacement | Captured existing report after parent lock; unexpected implicit report fails 40001 |
| Single-row payroll settings | Old/new worker/company; attendance months, statement periods, applicable current monthly period | BEFORE hook precedes payroll AFTER refresh, preserving existing RLS predicates |

All use the existing private helper ordering: company KEY SHARE, worker UPDATE, canonical company/worker/month advisory locks. Capture helpers are private SECURITY DEFINER with empty search paths and explicit PUBLIC/anon/authenticated execute revocation. They have no client endpoint. Tenant ownership is checked before any captured foreign-company parent is locked. Changed targets fail with 40001 rather than acquiring a new scope after waiting.

The settings BEFORE hook cannot precede PostgreSQL's initial target settings-row lock. It orders parents/months before the existing calculation AFTER triggers and covers the normal single-worker upsert. It does not claim arbitrary raw multirow statement or transaction-wide ordering. The existing generation-setting-issues AFTER trigger and all its business behavior remain untouched; the fixture does not validate that subsystem. Captured human-resource functions update worker/personnel/family rows without writing payroll settings. The actual professional portal saves through an approved edit invite without company membership; the hook adds no authorization condition, preserving that delegation and existing raw RLS. Before INSERT ON CONFLICT, an existing unique worker settings row is locked first to align with UPDATE. If a previously absent row appears during the parent-lock wait, 40001 refuses the changed target rather than taking its row lock late. Native cases exercise raw UPDATE versus actual delegated UPSERT in both start orders.

The isolated fixture installs the actual original eight entry definitions and existing calculators, resident resolver, finalization and document triggers. Synthetic dependency tables and notification sink permit exercising leave creation/decision, forced attendance, correction approval, signed destination replacement, cancellation audit and the captured settings RLS predicates. They do not prove actual production JWTs, Storage, external notifications, invoice/payment certificate calculations, complete production foreign keys or production schema compatibility.

Local PGlite integration and URL/syntax checks pass. Separate PostgreSQL 17 CI is prepared for reverse tuple force requests with stale retry, cancellation/signature contention, adjustment/finalization revision rejection and review/single-row settings serialization. Native concurrency results remain pending. The runtime permits only a named empty local disposable database with fixed fixture credentials.

Attachment/group/evidence/meter ancestors not included in the captured actual normal API definitions, service/admin raw attendance/leave bulk mutations, arbitrary payroll-settings bulk transactions, and all normal-entry coverage remain unresolved. No broad company gate or permission restriction is introduced. No payroll quantity, family eligibility, rate value or computed amount is inferred or seeded.
