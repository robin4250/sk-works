# Company payroll rate viewer read — staged adoption

The additional migration requires the exact latest company registry reader, admin guard and write function bodies. Unknown source/config differences fail before new DDL. It changes only rate reading; the original admin guard, manual save, candidate application and company-scope save bodies and grants stay unchanged. There is no production apply or official rate ingestion in this stage.

The new internal reader requires an authenticated user, the existing account-access guard returning true, an explicit same-company database membership with role owner/admin/viewer, and a live company row locked FOR KEY SHARE. A client-side viewer fallback for an unregistered user grants nothing. Manager/worker/other roles remain outside this page's reader contract. Foreign-company membership and stale membership after company deletion cannot read retained audit history.

`read_company_payroll_rates` retains the existing JSON keys and adds authoritative `can_edit: boolean`. Owner/admin receive true and the complete original data. Viewer receives false, the current items and latest existing verified candidate per item, including rate integers, application months, publisher/URL and checked time. Loading candidates does not apply rates. Company-scope value/version/updated_at remain visible, but updated_by is omitted. Viewer history and scope_history are empty arrays; audit actor IDs remain restricted to admin results. No personal pay, bank or family information is added.

The UI must require `can_edit == true` for write controls, without inferring permission from a local role. Missing can_edit is treated as false. Scope updated_by is nullable/optional for a viewer. Existing public and private writes continue to enforce owner/admin regardless of displayed controls. No raw-table grant is widened; the new internal reader helper has PUBLIC/anon/authenticated execution explicitly revoked.

The exact local PGlite fixture passes unchanged admin results (apart from can_edit), untouched admin/write function hashes/ACLs, viewer current-data visibility and all write rejections, actor projection, cross-company and nonmember/fallback refusal, blocked-account/anonymous refusal, live-company deletion with retained history and stale-membership refusal. A dedicated guarded PostgreSQL 17 job runs the same checks against an empty local disposable database. Its result is pending CI. Fixtures use synthetic account/membership prerequisites and are not production JWT or complete-schema proof.
