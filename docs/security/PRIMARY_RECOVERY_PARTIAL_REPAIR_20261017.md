# Logged-out primary password recovery: partial repair, not restored recovery

Base: 02cab526df266cfede7c991fd9ba162b9b335c7f. Production writes: none.

The existing primary-password forgotten action unconditionally switched to SMS OTP mode. Its repository signed in with phone OTP (`shouldCreateUser:false`), verified SMS to obtain an authenticated session, then used `auth.updateUser(password)`. The UI was not using Face ID on this path. History reviewed by the root agent includes #164 / 628474ce8 (phone-only SMS recovery introduction), #176 / ff2d8cb11 (immediate password update), and the ten commits returned for this file; this is not a claim that all branches or device-installed source history were exhaustively reviewed.

Face ID found in secondary-password setup/reset protects a different credential. Master emergency recovery requires an already signed-in user (`MasterRecoveryRepository.maybeCreate`), verifies local biometrics and secondary password, sends two configured email codes, and consumes their challenge to register a trusted Master device. It does not change the primary password or create a logged-out authentication session. Dual email contacts being unconfigured is accepted; this patch does not register them.

Root read-only production inspection reported password/recovery/biometric/passkey matching SQL functions limited to the existing dual-email and secondary-password functions, none executable by anonymous; the 16 listed Edge Functions contained only `send-master-recovery-codes` as recovery-related, with JWT verification enabled. No supported logged-out Face ID primary-password reset server authorization was found. This is bounded evidence, not an assertion that local biometrics can never be part of a separately authenticated recovery system.

This partial repair removes only primary-reset SMS request/verify methods and UI. Forgotten password now shows accurate unavailability with a return to login, clears password/code fields, offers no new-password entry, and makes no recovery request. It does not fake Face ID recovery or call updateUser after a local boolean or stored user ID. Primary recovery remains unresolved. Normal password login, administrator initial registration and its existing SMS verification/resend, employee QR login, authenticated employee initial-password update, secondary-password and Master recovery implementations remain available and unchanged in purpose. Existing registration SMS remains intentionally separate from the removed recovery route; this is not a declaration that all SMS was removed.

Before restoring the requested previous experience, identify the previously working installed app version/source and its actual server-verifiable login/recovery credential or session handling. A valid authenticated recovery capability is required; a local-auth success or preferences user ID alone is insufficient. Do not revive retired SMS, automatically register dual email, add new account recovery mechanisms, or alter Auth providers/admin roles as a substitute.

Tests: dedicated workflow analyzes the changed Dart files and runs actual Flutter widgets against the locked Supabase SDK with a synthetic HTTP mock. It checks forgotten-password API count zero and password update zero, unavailable UI/back behavior, ordinary phone-password authentication, and initial registration/OTP authentication. Source guards ensure reset-specific entry points are absent while employee initial update/QR remain. These checks do not prove successful real-device Face ID primary recovery or production delivery. Review the workflow results before integration.
