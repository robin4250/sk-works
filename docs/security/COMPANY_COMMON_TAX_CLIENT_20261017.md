# Separate company tax/welfare patch UI

New files only. Parent integration may embed `CompanyCommonTaxPage(companyId:
companyId, embedded: true)` in its tax/welfare tab. No existing route, payroll,
legacy four rates, old three allowance slots, DB/RLS/Auth/core or provider code is
changed by this client. Missing new APIs show preparation; the old full saver is
never called. Existing four-rate entry preservation belongs to the parent patch.

The two inputs are percentages: 10 means 10%, range 0..100 with up to four decimal
places. Integer-scaled editing avoids formatting 10% as 0.1. Read state has an
explicit company, catalog version, can_edit and exact immutable expected_source.
Its three legacy slots remain raw CAS values, including NULL, padded names and
free display units; tax edits never normalize or replace them.

Before every save the client freshly verifies read permission, can_edit, version
and source. Only owner/admin server permission allows writes; viewer is readonly.
A stale source keeps the draft and requires explicit review of latest saved
values before further editing. No automatic conflict merge or retry occurs.
The new patch sends exactly company/version/source/two rates/request UUID using
the captured session Authorization header. Actor switching invalidates the page,
closes its own review dialog and clears inputs. Company/dependency changes require
reopening. Initial background does no fetch; background hides fields and ignores
late results; resume rechecks permission while retaining a legitimate unsaved
draft. Same-actor remote role changes are checked on read/resume/before-save and
by the server, not pushed instantly into an idle foreground page.

Before a mutation RPC, an actor/company-keyed journal is serialized, file-flushed,
atomically renamed and read back. A process lock and file lock prevent overwrite
of another pending request. Its new app-support namespace never reads payroll
pending data. No credentials, tokens or employee data are persisted. A corrupt or
conflicting file blocks writes rather than being discarded. Temporary files are
recovered only after exact validation. Another actor cannot read/clear that record.

Unknown results survive reopening and permit receipt reads only, never re-sending.
A receipt must match tax operation, null payroll_type, actor/company/request,
expected version, complete request_payload and committed result/rates; a receipt
for allowances cannot clear a tax journal. Missing/mismatched receipts keep the
request blocked. Confirmed SQL rejections and missing-function responses permit
exact journal cleanup but preserve draft and require a fresh read. Already sent
HTTP is not physically cancelled; a valid historical receipt is followed by a
fresh read, so an older confirmed result is not presented as latest state.

The durability implementation targets native application-support files. File
flush/atomic rename/reopen/corruption and namespace isolation are tested in a
synthetic temporary directory. Physical power-loss/directory fsync behavior,
actual iPhone storage and Web persistence are not certified; unsupported file
storage fails closed before RPC. Dart strings are not guaranteed memory-zeroed.

The committed JSON fixture was generated by executing exact review-only backend
7282a180de60b949fcbd6b35a6a47ae779af1244 in a separate synthetic PGlite instance:
read -> tax-only save(8.5,12.3456) -> receipt -> missing -> viewer read. Tax-only
before/after snapshots prove only companies.tax_rate/default_welfare_rate changed;
old slots/IDs/history, membership/session, function definitions/ACL, payroll/daily
were unchanged. This does not certify real PostgREST/GoTrue/provider configuration.
Backend source, native races and its intentional legacy-unit compatibility change
are independently reviewed in #1152; production application remains prohibited.

New actual Widget, locked-SDK HTTP and native-file tests cover journal-before-RPC,
unknown/reopen/receipt mismatch, role/actor/company boundaries, duplicate callbacks,
background/late results, CAS draft preservation and missing API without fallback.
CI must pass at the exact head before integration. No production data or roles
are changed; full backup/restore/admin/provider and explicit approval gates remain.
