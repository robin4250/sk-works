# 第2パスワード再設定のサーバー境界検査（ベータ版）

この変更は隔離検査と設計レビューだけです。アプリ、Auth、RPC、実利用者の認証情報、本番DBを変更しません。検査成功は再認証対策の実装完了を意味しません。

## 確認した現行契約

- `SecureOnboardingRepository.setSecondaryPassword` は初期設定と再設定で同じ `set_secondary_password` RPCを使います。
- 再設定画面は本人確認を先に行います。Face ID / Touch ID、または本パスワードで確認します。バックグラウンド移行とactor変更で確認状態を破棄します。
- 本パスワードの確認は独立GoTrueクライアントで行い、その一時セッションだけを終了します。アプリのログインセッションは入れ替えません。
- 本番から読取した `set_secondary_password` は `auth.uid()`、8文字以上を確認した後、既存資格情報も上書きし、失敗回数とロックを解除します。再認証のnonce、期限、証跡を引数・本体に持ちません。
- `verify_secondary_password` は本人行を `FOR UPDATE` で読み、5回失敗で5分ロックします。暗号化方式は既存bcryptです。
- Data APIの既存pre-request hookは削除制限アカウントと並行削除のバリアを扱います。このhookを「再設定の本人再確認」の証拠にはしません。

## 隔離検査

専用PostgreSQL 17 serviceに本番読取関数のコピーと合成の認証主体を置きます。`authenticated` の直接呼出しで5回失敗のロック、直接setによる既存資格情報上書きとロック解除を検査します。他actorの検証、匿名、auth.uidなしは別に拒否を検査します。合成文字列以外のパスワード・JWT・QR・社員を使いません。接続先はloopbackと専用DB名に限定します。

この結果は関数のSQL境界の検査です。実JWTを使った本番HTTP検査、全重要RPC、セッション取消、Face IDのサーバー証明は未検証です。CIの状態はPRの最新headを確認してください。

## 最小修正を決める前提

初期設定と忘れた際の正常復旧を維持する必要があります。単にsetを禁止する、UIの確認済みbooleanを信頼する、JWT更新時刻だけを再認証と扱う変更は採用しません。

候補は初期設定と既存資格情報変更をサーバーで区別し、既存変更にはサーバーが確認して発行する短命・単回・actor/session/操作に結び付いた証跡を要求する方式です。発行と消費の同時実行、期限切れ、再送、actor切替、失効セッション、削除制限、正常復旧を否定検査する必要があります。

本パスワード復旧と、端末生体認証の復旧は同じ証明ではありません。Face IDの成功をサーバーで保証するには登録された端末鍵などの別契約が必要で、クライアントの成功フラグでは代用しません。現在の正常導線を保つ方法が決まってから実装します。

このレビューでは既存 `SECURITY DEFINER` を一律変更せず、権限・保存先・暗号化・role・復旧機能を保持しています。
