# Platform log monitor: staged server boundary

Distinct from synthetic incident records. Nothing in this change enables production monitoring, creates credentials, reads live log rows, sends notifications, changes a business table/RLS policy, or relabels synthetic evidence.

`platform_log_adapter.mjs` is a server-only importable adapter for the official Management API GET `/v1/projects/{ref}/analytics/endpoints/logs`. Its fixed ClickHouse projections select only IDs/timestamps, gateway status/path, or Postgres SQLSTATE; never `event_message`, SQL query, request/response headers, body, IP, email, or auth tokens. At most 15 minutes and 1000 rows; 10-second timeout, 1MiB streamed-response bound, redirects rejected. The caller obtains a scoped server Management API/OAuth credential independently. Never put a management credential or HMAC key into Flutter, JavaScript shipped to users, logs, fixtures, or source.

Official API/reference rechecked 2026-10-16: https://supabase.com/docs/guides/observability/advanced-log-filtering and https://supabase.com/docs/reference/api/v1-get-project-logs . This adapter requires ClickHouse; do not silently substitute legacy BigQuery SQL. Live schema/query compatibility is not yet verified against project rows.

IDs/paths are HMAC-SHA256 pseudonyms, scoped by source/type and explicit key epoch. Query strings/fragments are stripped before path hashing. The target is not a known identity/tenant; no actor/company attribution is inferred. Raw paths are transient server input and never persisted or returned. `source_key` is currently null and `source_tracking` is explicitly `unavailable`: this adapter does not establish trusted ingress identity. It never trusts client X-Forwarded-For/x-real-ip/CF-like headers or fetches raw IPs. Repeated-source tracking is not implemented; a future adapter must prove the platform ingress trust boundary before producing an origin pseudonym. Rotating a key starts a distinct pseudonym epoch; this does not prove one person or deduplicate across epochs.

Source provenance is `supabase_platform_logs`; `http_success` means only HTTP 2xx, `forbidden` only HTTP 403, `permission_denied` only SQLSTATE 42501, `unknown` means unknown. Neither a 200/empty RLS result nor 42501 proves an attack, RLS bypass or the reason for denial. Auth audit rows currently retain only date/source/pseudonym with result unknown. No automatic blocking or attack-confirmation UI is provided.

The default-OFF private control has no client setter. The only ingestion API is service-role-only and invokes a strict metadata validator. Ordinary users cannot manufacture platform records. Windows have exact canonical payload digests, replay idempotency/conflict checks, 1000 events/window, 10000 retained events and 1000 retained windows; a capacity error rolls back the whole batch rather than silently evicting evidence. A returned 1000-row result reaches the documented query limit and is conservatively `capacity_limited`, even when no omitted row can be proven. It is never complete coverage. A bounded query is not proof of continuous monitoring, even when empty. Provider loss, collection gaps, restarts, source availability and durable scheduling require separate operational verification.

The separate master read RPC `master_platform_security_monitor(p_proof)` checks current enabled account and master on the server, then atomically consumes auth-lane proof for `master.security_incidents.read` with target `{"scope":"platform"}`. That proof contract is a prerequisite, not bundled or stubbed in the migration. Until the real helper and its tests are integrated, rollout stays OFF. The fixed platform scope is intentionally operator-wide and never exposed to tenant administrators; no caller-selected company ID is accepted. Existing synthetic records/UI/RPCs are unchanged.

Read returns only the latest 100 events/windows from seven days with explicit source and coverage limits. Purging occurs on a successful ingestion transaction; no scheduler is provisioned, so stopped ingestion does not guarantee physical deletion at seven days. A reviewed service-only scheduled purge, freshness alarms, verified overlap/backfill policy, trusted deployment/isolation and rotation procedures remain release gates for a claim of continuous monitoring.

Validation: Node unit/actual loopback upstream HTTP transport tests; PGlite exact SQL role/default-OFF/replay/privacy checks; CI repeats the SQL against disposable PostgreSQL 17 and a real PostgREST 16.4 signed-JWT HTTP boundary (anonymous, wrong signature, expired, non-master, disabled, service ingestion, consumed proof). These fixtures use explicit fake master/account/proof helpers. They do not validate live GoTrue session revocation or auth-lane nonce issuance, real source records, production credentials, scheduler or device UI. Do not present these as deployed or production end-to-end monitoring.

## Existing identity/settings protection and structural rollback

Production permission, authentication-provider, administrator/member/role/company, Apple/Google and UI settings are outside this change. Before any production change, the operator must have an authorized encrypted snapshot, a successful isolated restore, normal-admin/current-UI comparison, an impact report and explicit approval. No fixture result substitutes for those prerequisites.

`platform_monitor_rollback.sql.review-only` is a non-automatic structural removal proposal, not a migration or approved production command. It demands a verified-restore acknowledgement and disabled new control, refuses any nonempty new evidence table, locks the control, and drops only the four new functions and three new empty platform tables. It has no `CASCADE`, grants/revokes, original data deletion, original role/membership/master/provider edits, or change to the proof/auth foundation. Unexpected dependent objects abort the transaction. Populated evidence needs a separate preservation/retention decision; this script never deletes it.

The isolated restore test creates fake protected company/member/admin/master/Apple/Google/synthetic fixtures, snapshots their values plus all fixture table RLS/ACL/owners, role attributes, policies and function definitions, then applies/tests/removes the new platform foundation. Missing acknowledgement, enabled control and nonempty evidence refuse; refusal preserves evidence. After fixture-only removal of disposable evidence and structural rollback, the protected fixture snapshot matches exactly. These are artificial values, not real administrator IDs or a live project snapshot. Real OAuth login and the full normal-admin UI still require the independent release/restore lane's verification.


## Unified API compatibility correction

The former `analytics/endpoints/logs.all` endpoint is removed (410 Gone), not a valid ClickHouse transport. The current `v1-get-project-logs` reference specifies `analytics/endpoints/logs`, ClickHouse SQL, `source` and minute-rounded time parameters, response `{result, error}`, OAuth `analytics:read` or fine-grained `analytics_logs_read`. The adapter uses only that endpoint and never falls back. The July migration announcement still illustrates `source_name`; current API and field reference both specify `source`, which is the schema used here. References: https://supabase.com/docs/reference/api/v1-get-project-logs-all ; https://supabase.com/changelog/48235-migration-of-supabase-management-api-logs-all-analytics-endpoint-to-logs-endpoint ; https://supabase.com/docs/guides/observability/log-field-reference .

API time parameters enclose the requested interval by flooring start/ceiling end to UTC minutes. SQL adds exact half-open DateTime64 UTC bounds, preserving subminute/millisecond boundaries. Request/response status/path and Postgres SQLSTATE map keys match the current field/SQL guides. DateTime64 UTC timestamps support documented ISO strings and ordinary ClickHouse UTC space-separated output; no local timezone is inferred. Source headers/IP trust remains unverified and `source_tracking=unavailable` is unchanged.

The dedicated workflow additionally executes the actual SQL against a disposable ClickHouse 25.3 unified `logs` fixture with all three sources and microsecond boundary records. The Management API HTTP server/authorization remains fixture-only; current API/schema documentation compliance plus engine success must not be described as production collection. Real source query compatibility remains unverified because live raw logs and credentials are deliberately not retrieved.

The auth `master_security` scope gate is global, not per-company or per-user. Existing Apple/Google-only users without a primary password have no supported proof alternative in this candidate. Keep that scope OFF until an independently verified alternative exists; never enable it merely because password-account fixture tests passed. Production authorization changes remain prohibited before the authorized snapshot, successful isolated restore, normal-admin UI comparison, impact report and explicit approval.

## Timestamp precision compatibility

Read-only aggregate evidence from 2026-10-16 found UUID identifiers and DateTime64(9) timestamps for all three platform sources. A timestamp-only serializer sample had six fractional digits, T separator and no Z; the existing adapter already accepted that sample. This change is compatibility hardening, not evidence that current production collection fails. No raw event, actor, ID, URL or credential was obtained for these fixtures.

The adapter now accepts one through nine fractional digits in UTC output. Occurrence timestamps are normalized to milliseconds for the existing storage/UI contract; nanosecond precision is not retained. Distinct source IDs remain distinct HMAC event identities even within one millisecond. SQL performs exact half-open filtering before normalization. A real disposable ClickHouse UUID/DateTime64(9) fixture verifies records one nanosecond before start/end, exact endpoints and source projections. Management API authorization/serialization is still fixture transport; this does not enable or deploy production collection.
