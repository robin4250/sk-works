# 社内共通手当の給与計算接続候補

既存共通手当保存候補 `tool/staged_company_common_allowances.sql.review-only` の extras は給与計算で参照されていなかった。本候補はその新規項目だけを `payroll_unit_private.augment_settings` に合流させる。旧3枠、個別の既存手当、税計算、明細の既存経路を再実装しない。新しい価格マスターは作らない。

給与形態 daily/hourly/monthly を個別設定と一致させ、日単位は正の人工が登録された実出勤日を同日1日、月単位は1、時間単位は共通項目のstable IDに対応した明示的な当月hoursを使う。人工×8の推測はしない。未入力hoursはnullとして計算未完了にする。内訳に会社共通のoriginとstable IDを保存し、共通支給・共通控除を合計・差引に接続する。既存税計算はその支給額を使う。

`payroll_activation` は直接clientアクセス不可、有効会社行は0が初期値。会社ごとの開始月をレビューして初めて有効になる。開始月以前に現在単価を適用しない。本候補の実行自体は既存帳票を再計算しない。関数は既存OID/owner/ACLを保持、追加helperはclient非公開。適用開始月・有効化の書込みや本番DDLは本検証では一切行っていない。

検証は既存給与fixture・原本unit/tax SQL・既存共通保存候補の原本storage DDLを使用。実refresh経路で支給/控除/差引、同日複数現場、未入力時間のblocked、入力時間の反映、給与形態の混同なし、未有効会社・開始前月の保持、再実行revision不変、廃止項目、源泉税への合流、実確定APIで確定後の内訳不変、関数ACL/OID保持を確認する。共通手当の保存API/Authそのもの、実JWT、実PDF/実機、本番の完全backup/restoreの検証ではない。

## 残る実装と適用条件

これは計算接続のreview-only部品であり、社内共通手当の利用完成ではない。

- 既存共通手当基盤およびidentity基盤が本番未導入。`company_common_allowance_predeployment_20261017.md` の既存依存・保護・復元条件を引き続き満たす必要がある。
- 個別単位別設定画面に共通項目を折りたたみ表示し、時間数量だけを `save_payroll_common_hours` で保存する候補を追加。既存認可・会社/従業員ロック・対象月・確定/手入力給与保護・完全source CAS・共通ID限定を守り、保存後に既存refresh/syncで当月を再計算する。既存個別IDの検証は緩和しない。SDKは元tokenに固定し、同じtokenでのログアウト→再ログインでも旧応答を破棄する。未入力の他共通時間項目があればblockedは残る。候補のUI/SDK/本番接続テストは別途確認する。
- 個別上書き／共通金額変更の適用月／会社共通保存後にどの自動下書きを再計算するかを、既存履歴保護と整合する契約へ接続する必要がある。同名を根拠に既存個別項目を勝手に置換しない。
- 有効化後に作成した合法的な給与履歴がある状態でDDLを削除するrollbackは不可。次段階は非公開backup・適用／復旧検証、個別金額上書きと会社共通保存後の自動再計算の実装である。
