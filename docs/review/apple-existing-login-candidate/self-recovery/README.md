# Apple self-recovery orchestration — isolated, OFF

The existing recovery function remains restricted to a root operator. This candidate demonstrates the required caller-side checks before an owner may request reconciliation: exact verified original session, request ownership and held status, fresh primary-password verification that closes its temporary session, and a server-generated command bound to actor, original session and request. A separate root-only SQL candidate persists the command across uncertain responses and refuses other accounts or sessions. It returns a generic review state unless the trusted reconciliation confirms completion or cancellation. Cancellation requires a newly authenticated Apple credential; it never permits replay of the old token.

This is not a usable recovery endpoint. The PostgreSQL adapter connects fixed-parameter queries to the existing root-only routines, in isolated PostgreSQL/PGlite fixtures. It deliberately uses the exact root authority required by the existing routine; a root database pool is unsuitable for a production endpoint. The call-site must be trusted and the privileged boundary must be redesigned before deployment. The command registry is append-only; reconciliation preserves its original Auth lock order. The real proof issuance, production-safe operator adapter, durable rate limiting, least-privilege operator boundary, user interface, real GoTrue, on-device verification and production safety/rollback are absent. Do not supply true gates or connect privileged ports until these are implemented and reviewed. No production Auth, roles, grants, sessions or identities are changed.

On retry the root function can return a recorded result before checking the live account. The new isolated wrapper takes the existing reconciliation locks in order, holds the account and session rows and checks live context before returning even a prior result. Concurrent ban and session deletion tests require Native CI; other Auth writers and production load are not proven. The inherited identity-table and membership locks affect the whole deployment and MUST NOT be enabled in production without a safe concurrency design, catalog review and a least-privilege operator boundary.
