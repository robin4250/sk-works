# 経費方向v2の適用前限定・コード復元候補

既v2候補を変更せず、コードだけの復元準備を独立support branchへ保存する。製品migration・公開API・本番接続・有効化・実行の追加ではない。

`expense_direction_code_checkpoint.mjs` は、既3関数と新5関数の完全定義/OID/owner/ACL/実行属性、対象trigger、event triggerをcatalogから読み、before/after一致を必須とする単一DOの復元SQL文字列を作る。module importや生成だけでは接続も実行もしない。署名はsearch_pathに依存しないschema付きへ正規化する。原本は信頼できるオペレーターが採取したcheckpointだけを使用する。任意の外部JSONを認証済みAPI入力として受け付ける機能ではない。

許可するのは既3関数のmetadataが保持され、適用後gateが既定falseで、新方式帳票が一件もなく、旧下書き変換機構が未導入の状態だけ。支払表のSHARE ROW EXCLUSIVE lock後にafter完全一致を検査し、v2/basis付きrowがあれば下書き/確定を問わず拒否する。3原本定義の差替え後、追加5関数と新guard triggerだけをCASCADEなしで削除し、before完全一致を再確認する。未知依存があれば途中の原本差替えも同じstatement内でrollbackする。業務行のINSERT/UPDATE/DELETE、revision巻戻し、audit/消費削除は一切生成しない。

既存v1の確定帳票・実消費履歴を含む合成fixtureで、正常復元とデータ不変、ACL/関数属性/trigger/gate変化の拒否、未知view依存の拒否と全コードrollback、新方式draft/finalizedの拒否、変換機構存在時の拒否を検査する。PGlite検証を実施し、同じ検証を既localhost専用PostgreSQL17 adapterへ入力して専用CIで実行する。

初回PGliteはpublic関数のregprocedure表記がsearch_pathで非修飾になり拒否した。schema名と引数型からcanonical署名を構成して再検証成功。失敗を本番不具合と混同しない。

現原本ZIPのbackupは別途保持する。本toolのbefore/after catalog形式をそのZIPへ無検査で代用しない。将来適用時は同時点の再照合と配備後checkpointが必要。実production復元試験・役割/JWT・RLS・旧client遮断・実row保護・完全helper closureの証明ではない。非協調の管理者DDLやlock後の全操作を全局的に直列化する保証もなく、実運用は保守時間・変更担当の調整と明示承認の別工程。v2データ発生後はこの復元SQLを使わず、v2 reader/guardを残す前進修復が必要。
