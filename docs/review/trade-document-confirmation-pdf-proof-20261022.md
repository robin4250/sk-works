# Real approved-document PDF verification candidate

The client parser tests alone stop at `approvedAttachment`. The separate
`test/trade_document_confirmation_pdf_test.dart` calls the actual
`TradeConfirmationPdf.approved` renderer, including the real registered seal
parser, real pinned font asset, order/acceptance layout and PDF serialization.
No renderer dependency, font mock or invented attachment is substituted.

## Input and execution

The input is the API lane's unchanged synthetic SQL export at
`test/fixtures/trade_document_confirmation_api_synthetic.json`. It must contain
the actual `issued_render`, `received_render`, `invoice_render` and
`invoice_received_render` responses. A missing response is a test failure rather
than a skipped or fabricated acceptance case. This exercises both order and
acceptance, each with a separate issued/received local page identity.

Root owns remote execution, workflow and the pinned font bootstrap. Use the
repository's locked Flutter/dependencies and genuine
`assets/fonts/company-seal/NotoSansJP-Bold.ttf` asset. The test never fetches an
unverified font or falls back to a different one.

Set `SKO_TRADE_CONFIRMATION_PDF_OUTPUT_DIR` to a new CI artifact directory and run:

```text
flutter test test/trade_document_confirmation_pdf_test.dart
```

Without the output variable the test still performs all real PDF generation in
memory. Export is optional; real rendering is not optional. The local agent must
not run Flutter/Dart under the existing execution restriction.

## Export contract for independent verification

`manifest.json` contains schema 1, `synthetic_fixture: true`, the unchanged source
fixture SHA256 and four file entries. The fixed file names are:

```text
order-issued.pdf
order-received.pdf
acceptance-issued.pdf
acceptance-received.pdf
```

Each entry records one expected page, required visible text, PDF hash, evidence
ID/revision/body hash, distinct local ID, side, issuer/counterparty name, source
amount/tax, renderer contract and registered stamp style. Uploaded PNG cases also
write the exact validated registered PNG as `*-registered-seal.png` and record its
SHA256 and dimensions. At least the issued/received order pair must exercise a
registered PNG. Nothing is taken from current company settings after approval.

The source response is checked unchanged after real generation. Each kind's
issued and received payload must match; its evidence ID matches and its local IDs
must differ. Preview, printing and sharing use these same generated bytes within
each client page. Separate PDF serializations can have different file hashes due
to document metadata, so no cross-company byte-identity claim is made.

## Independent PDF and visual checks

Root should use its pinned PyMuPDF/Poppler verification to:

1. Reopen every actual PDF, verify its exported hash and one-page A4 geometry,
   locate required company names, addresses, corporate numbers, representative
   names, work name/place and issue date, and reject text/image bounds outside the
   page.
2. For orders, require the source total and included tax values in visible text.
   The existing accepted acceptance template does not have separate amount/tax
   fields: `amount_fields_visible` is explicitly false there. Its source values
   remain unchanged in the payload and manifest; this test does not invent a
   visible amount field or silently change the adopted template.
3. For registered PNGs, verify the exported original file SHA, extract the PDF's
   actual image and alpha mask, check dimensions and compare decoded pixels with
   the registered PNG. PDF recompression need not preserve the PNG file encoding;
   image presence alone is insufficient. Ignore RGB values only where both
   compared alpha values are fully transparent; do not ignore visible pixels.
4. Render all four pages to PNG and inspect spacing, company/representative
   fields, stamp position and clipping. Text extraction is not visual proof.

This is a synthetic content/renderer proof. It does not establish the appearance
of a real user's uploaded seal, native iPhone printing/sharing, live JWT/session
authorization, production deployment or consent completion on a user's document.
No success is claimed until this exact candidate's CI and visual checks pass.
