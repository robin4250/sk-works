# Invoice explicit surname-only personal seals (staged OFF)

`user_profiles.display_name` and approval identity/time/history remain unchanged. No Japanese full name is guessed or split. The pending approver enters their own `承認印に表示する名字` in the existing invoice approval flow. Existing approver configuration and approval rights are unchanged; even invoice managers cannot edit another person's surname here.

A separate private per-invoice draft stores the explicit surname. The new approval wrapper serializes company → invoice → rollout gate, rechecks exact-invoice membership, calls the existing `approve_invoice`, and captures its actual timestamp and surname in the same transaction. Snapshots are keyed by invoice, approver and actual approval timestamp. Repeated approval does not add snapshots. Cancel/reapprove creates a new timestamp version; the prior snapshot and explicit-input history remain. Existing approval RPCs and RLS policies are not replaced.

No backfill or initial rollout enablement. Existing approved rows, unconfigured rows and installations without the new RPC retain the original role/date/name seal layout and show an unset notice. Only an actual surname snapshot uses the new surname-only circle. Later profile or draft changes do not change an old snapshot. Turning the rollout OFF blocks new surname input/approval-wrapper writes while keeping saved snapshot reads and old seals intact. A company gate here is deployment readiness, not the postponed Master ON/OFF product design.

The getter delegates exact-invoice authorization to the existing v2 RPC. It returns configured draft names only to their own pending approver; other people see only approved snapshots. New private tables enable RLS and revoke client table privileges. New public RPCs revoke PUBLIC/anon execution, grant authenticated, and use an empty search path with explicit schemas. No profile/Auth/old-table RLS changes. Company/invoice deletion follows existing invoice retention/cascade behavior; this is not a redesign of deletion retention.

Synthetic PGlite loads both real existing approval migrations and exercises OFF, exact company, own pending access, malformed/empty explicit names, missing-name refusal, approved retry, profile change, OFF saved read, cancel/reapprove version preservation and direct table ACL denial. CI also generates real invoice PDFs for explicit joined-name, legacy joined-name, pending and snapshot names, preserving A4/amounts and approval metadata. Local Flutter is unavailable. CI/PNG and independent review are required before merging; production application, activation and actual phone operations are separate and unverified.
