# New private monthly content review and issuer seal proof

This is a newly designed isolated candidate, not a connection to an existing monthly financial approval API. The source/catalog investigation is in `monthly-payment-confirmation-contract-20261022.md`. There is no public endpoint, grant, UI, production installation, company request or financial-parent update.

## Exact meaning of the new result

`trade_document_consent_private.confirm_monthly_review` records an explicit review of the current stored monthly certificate content and the issuer's own registered-seal consent in one transaction. It returns `monthly_review_recorded=true`, `seal_consent_recorded=true`, **`financial_finalized=false`**, `financial_parent_unchanged=true`. This is deliberately not a substitute for the still-missing financial approval/finalization transaction or complete recipient confirmation workflow. It does not update certificate status, amounts, details, expense consumption, existing financial triggers or assigned approver records.

One owner-only immutable table `monthly_review_receipts` is added inside the existing private consent schema. The new `monthly_binding`, `monthly_view_allowed`, `preview_monthly_review` and `confirm_monthly_review` functions are revoked from PUBLIC/anon/authenticated/service_role. RLS is enabled without a client policy. The original unconnected `confirm_local_document` monthly branch remains unchanged; existing invoice confirmation continues through its existing coordinator.

The two existing private callbacks `parent_binding` and `linked_view_allowed` receive a narrowly added monthly branch. Their exact prior bodies, owner, security, language, execution attributes, return type, empty search path and absence of client execution are prerequisites. The fixture also compares their complete original pg_proc attributes after replacement. The unchanged original invoice callback branches remain present. The issuer preview additionally invokes the actual private source reader to check the attachment source fingerprint, including a parent change that did not increment revision. No alternate financial writer or public authorization adapter is invented.

## Binding and authority

- A stored UUID parent owned by the issuer, its revision and full parent fingerprint, period/snapshot/financial contents, saved attachment version/source revision/payload fingerprint, directional order document revision/body hash/epoch and current official seal version/hash are bound. In-memory `preview:...` identifiers cannot enter UUID APIs.
- The local partner record resolves through a unique same-company `trade_companies.partner_company_id` row with `subcontractor`/`both`, `linked` and exact `linked_company_id`. The actual consent core's accepted formal connection check remains mandatory.
- Only the issuer's current owner/admin with allowed account state may preview/confirm its order. A received company cannot consent to the issuer's seal. Each company binds its own distinct local page ID. Belonging to both companies does not replay another actor's receipt.
- A received owner/admin can read the same approved issued evidence through its own local ID only after a monthly review receipt exists. Calling the private core seal primitive alone cannot unlock monthly printing. `monthly_binding` is owner-only internal data projection, not an exposed caller API; preview/confirmation and current/archive rendering enforce their respective issuer/received permissions before invoking it.
- The same actor/request/payload replays the immutable result before stale-current checks. Changed actor or payload rejects. A later parent change cannot rewrite the old receipt, body or seal snapshot; current rendering rejects and explicit archive retains the saved evidence.
- Company locks precede parent/attachment locks and the existing document advisory lock. Both explicit choices, fresh preview equality, final parent equality and receipt insertion occur in the same transaction. A later receipt-insert failure rolls back seal consent and all new review evidence.
