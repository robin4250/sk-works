# Attendance management: authenticate once on entry

Base main `74d4c2f578e26ca1f7f21628f19a1da6b2fdeee9`. This is a new **unpublished-to-device, default-OFF candidate**. It does not alter the preserved build20 IPA or enable any production flag.

## Confirmed mismatch and intended behavior

The existing protected route already asks for secondary authentication when opening attendance management. However, the additional `attendance_management` operation-proof flag would make each upsert/delete ask for a password again. This contradicts the clarified requirement. That global operation-proof flag must remain OFF.

This candidate uses the existing real password verifier once at the page entrance. Its established failed-attempt counter is committed by returning structured failure; a failed password is not followed by an exception that would undo the counter. Successful entry returns an unpredictable 256-bit token held only in that page repository's memory. The server stores its SHA256 hash, never the token or password. Authenticated live SID, exact company, current management role/feature, credential fingerprint, company admission revision and fixed 15-minute maximum lifetime are checked again for every management request. The unchanged underlying writer retains management audit, source/signature handling and financial refresh. No password prompt is shown by the management action buttons.

Backgrounding, route disposal, auth history change, expiry and ambiguous write failure clear the local token. Revocation is best effort; server expiry, credential/role/session checks remain authoritative if the network fails. Re-entering after expiry/background requires another entrance check. The candidate never caches the password. A local Face ID boolean cannot mint a server grant: when the new entry gate is ON this management entrance uses the secondary password; ordinary Google/Face ID login and other existing protected routes are unchanged.

The new company gate is separate from the old global per-operation proof flag. New clients use the old entrance behavior only when the additive entry API is genuinely absent (`PGRST202`) or explicitly OFF; permission/network/malformed responses do not downgrade. Old two-argument and operation-proof writer APIs refuse requests for a company whose new entry gate is ON. The new authorized writer calls the same private original management writer after all grant checks; it does not impersonate a manager using a client boolean.

Changing the company's admission revision invalidates every old grant. The explicit revoke-all RPC requires an existing valid entry grant, owner/admin role, exact company/revision and a reason, and records an audit event. Any OFF/ON gate transition also advances the revision, so disabled grants cannot come back into use on reactivation. This is a bounded authorization mechanism, not proof that an external WAF or infrastructure MTD is deployed.

Protected-page tests cover one entrance prompt, repeated child actions and background locking. Verified implementation head `f6f9fe60ffd686840c569a2d846239c5c21b0d6e`, dedicated run40283157538: Native138 checks, client32 tests plus protected-page widget1 test, analysis without issues. Subsequent exact-source/metadata restore guards are separately validated at the final published head; no deployment or device success is implied.

Install captures the existing two public function definitions/full pg_proc metadata and retains their OIDs/ACLs. All new schema objects are private, RLS protected and deny direct client/service access. Restore refuses any configured gate, grant or event and any changed original/new function metadata or module table/schema/RLS/ACL/column/constraint/index/trigger/policy catalogue. It uses reverse-order DROP without CASCADE; unknown dependencies abort the transaction. Production original/table/catalog comparison and durable backup are the root owner's separate deployment responsibility.
