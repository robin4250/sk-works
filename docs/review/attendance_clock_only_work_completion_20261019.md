# 打刻のみの日の勤務補完

基準 main a7c9647。報告済みの3日打刻/2日給与は、不足日に給与用attendance_entriesがないという既存調査を引き継ぐ。実対象の新規日報・署名・勤務・給与を勝手に作らない。

既存勤怠管理loadCellは勤務行がある場合だけ打刻を取得し、勤務行も承認済み有給もない日は常に休みへ落としていた。勤務行なしの限定読取でも、既存の会社/社員/業務日スコープで打刻を取得する。打刻があれば画面内の未確定状態とし、保存済み出退勤時刻を表示する。複数現場は勝手に1現場を選ばず、人工は入力を要求する。承認済み有給と勤務ありの従来経路は維持。打刻取得失敗は休みへ置換せずエラーにする。

未確定のまま休みとして上書きする操作は拒否する。管理者が出勤・現場・人工・内容を確認した後の書込は既force_manage_attendance経路のまま。既存の明示削除確認は残る。社員/日付を切り替えた後の旧読取結果はgenerationで破棄し、取得失敗/取得中のフォームから更新しない。日本語ヘルプと英訳を追補。

実SDKの隔離HTTPで勤務2日/打刻のみ1日、会社社員scope、数量未補完、書込0、権限拒否、有給/空日/複数現場を検証。実画面で未確定案内・旧休みupsert拒否、旧社員の遅延結果拒否を検査。新4件と既契約3件、計7件成功。初回HTTP fixtureはResponse.request欠落、widget fixtureはSDKをfake asyncで生成した終了待ちが原因で失敗し、実コードの拒否条件を弱めずfixtureを補正した。失敗ログは作業領域へ保持。

この変更は不足勤務を見つけて既存管理導線から補完する準備であり、実対象13日分の勤務確定・給与再計算・実機3日反映の完了ではない。SQL/本番/給与金額/署名/既確定帳票の変更0。日報による通常確定経路と、管理者直接補完の既存権限・副作用は区別する。
