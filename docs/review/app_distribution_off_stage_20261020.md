# SKO invitation distribution — OFF installation and pre-use rollback

This candidate reuses `app_distribution_channels_20261020.sql.review-only` from #1284. It changes no distribution business function body, creates no configured URL, and activates no invitation. The existing 69-assertion verifier is reused unchanged. It is not a second invitation implementation.

Read-only production review on 2026-10-20 confirmed legacy settings OFF/public OFF/URL empty, the legacy dispatcher body hash matches `3ccced6e2d9a82d715e07c6b3f25b490`, and the four channel RPCs/two private channel tables are absent. Consequently the current client cannot use its modern channel APIs merely by setting a flag ON.

The install bundle adds a guarded stage before the existing schema and function installation, with the existing source-hash check still first. It locks the settings singleton, requires both flags OFF and the legacy URL empty, and verifies unchanged OFF/empty settings and empty new channel records before commit. Existing settings, invitation history and legacy RPC signatures are preserved. PostgREST cache reload is requested inside the transaction. Arbitrary inherited default grants still fail the existing ACL checks and roll back the whole installation.

The undo candidate is deliberately limited to the **unused, unconfigured, OFF** state. It refuses saved URLs, either enabled flag, issued channel invitation metadata, changed function bodies or dependent objects. It restores only the exact backed-up legacy dispatcher body, preserving its owner/ACL, and removes only the unused newly added APIs/tables. It does not delete legacy settings, invitation records, membership, credentials or company links. After URL configuration or use, stop distribution using the existing OFF flag; preserve records and review a data-aware restoration instead of unconditional DROP.

Before any production application, save and verify a private backup of the exact settings singleton, legacy dispatcher definition/owner/ACL and all invitation-history dependencies; record counts/digests without exposing phones or URLs. Recheck candidate-object absence, source hash, inherited grants and current flags. This work has not applied SQL, changed flags, registered a URL, sent a message or linked companies.

The legacy snapshot fallback remains available only for the actual missing-function code PGRST202, preserving existing scoped history. Legacy preparation cannot establish a company connection, and friend invitation fallback remains closed in the current client. A forthcoming opaque company-invitation bridge must not silently substitute the legacy generic invitation number for a company-link token.

Real TestFlight distribution still requires an approved, usable URL and Apple tester eligibility. No production-format eight-character TestFlight join URL was found in the reviewed local text records after removing fixture/test examples; none was invented. Sending an invitation does not create company membership, friendship, registration attribution, points or a company link. A cooperating company registers its own account/company and explicitly requests a link; the other company must approve.

Validation runs the unchanged 69 compatibility assertions plus 19 new stage/undo assertions against PGlite and separately isolated empty PostgreSQL 17 databases. The native adapter/URL guard is reused from #1284. The fixture verifies exact settings preservation, unsafe install refusals, exact legacy hash/ACL restoration, and refusal after URL configuration or function drift. All URLs, phones and users in the tests are synthetic.
