# Company work-category input defaults

Base: main `112b989978b2f784e66854d12315fec649ecbadf`. This candidate supplies a missing company setting and proposes new day/night/holiday/holiday-night input from the saved clock-in. It never rewrites an existing report, signature, clock, attendance, payroll, invoice, or finalized value.

The existing company-data profile and rate settings do not store night boundaries or holiday rules. Rather than overloading optional module booleans or financial rate fields, the candidate adds two private tables and explicit company-scoped read/save RPCs. Installation is a single transaction and inserts no company policy. Absence is OFF: a user must explicitly save company settings before any automatic proposal is available.

Installation requires the exact reviewed `private.require_reauthentication_session()` from the core-proof module (body/owner/config/ACL pinned); therefore apply this candidate after core proof. Both RPCs reuse that helper and explicitly require `private.account_access_allowed() IS TRUE`, so stopped/deleting, anonymous, banned, signed-out/missing/expired/foreign-session accounts fail closed. No OAuth/JWT claims supplied by clients are accepted as company roles. `service_role` is explicitly revoked from schema/tables/private functions and public RPCs.

Only one live membership for the explicit company is accepted. Members may read their company settings; owner/admin may save with the expected revision. Role edits are held with a membership SHARE lock, concurrent initial/update saves serialize per company, and stale writes conflict. Each successful save creates an immutable private history revision. No anonymous RPC access or direct authenticated access to private tables is granted. Private tables have RLS and no direct policies.

The administrator form starts with an unsaved editing example (22:00–05:00, Sunday, national holidays OFF), clearly labelled as unapplied. There are no hidden payroll defaults. The administrator chooses the actual company rule and saves it explicitly. Japanese holiday adoption is opt-in. Explicit working dates override weekdays/holiday calendar; a date cannot simultaneously appear in additional holidays and working exceptions.

`CompanyWorkCategoryRepository.load(companyId)` returns a policy or `null`. `proposeForSource(snapshot, sourceClockInId:, workerId:, workDate:)` reads the actual clock-in using existing verification RLS, checks company/worker/source/event/work date, requires a timestamp with timezone, and classifies its instant in JST. The loaded snapshot is bound to its UID/session identity; a later account/session cannot reuse the old settings form or proposal. Missing policy, missing or mismatching source, unavailable RPC, auth-history change, or read denial does not authorize an invented value. The UI retains manual category entry. Already saved categories must take precedence and are never overwritten.

Night windows include start and exclude end, supporting both crossing-midnight and same-day windows. The saved source work date determines holiday status, not the date on the device or the next-day checkout. These remain editable input proposals, never proof that the shift was worked or manager approval.

Validation is in `.github/workflows/company-work-category-policy.yml`: focused Flutter analysis/policy tests and an isolated PostgreSQL 17 test for authorization, validation, audit/CAS concurrency, default absence, unused restore/reinstall, and refusal to restore after use. No local Flutter/Dart is run. Actual CI results are recorded separately.

`restore_unused.sql.review-only` is only for unused settings/history, matches the exact three routine bodies, drops in reverse dependency order without CASCADE, and refuses used policy. It is not an online undo of settings that a company has saved. No production application, activation, actual company setting, release, or iPhone verification has been done by this candidate.
