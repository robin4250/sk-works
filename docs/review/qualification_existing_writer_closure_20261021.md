## DELETEとStorageは別の保護

20260919024500_harden_qualification_rls.sqlの「managers can manage worker qualifications」はowner/admin/managerのFOR ALL（DELETEを含む）。最新本番の全policy/ACL一致をこのsourceレビューだけで証明しない。DELETEをguard素通しに戻すと、添付の正式参照を未承認で消せる。履歴やStorage bytesが残ることは、正式参照削除の承認ではない。

20261010222753_protect_qualification_photo_snapshots.sqlはAFTER DELETE/UPDATEで旧写真をqualification_photo_historyへ記録し、現row/history/旧worker履歴/delivery/queue.previous参照をStorageのrestrictive delete/update policyで保護する。20261010233011はphoto_paths/upload_pathsも保護する。既candidateはこれらStorage方針を変更しない。全DELETE拒否を維持し、cascadeを黙って例外にしない。退職等の保守運用が止まらないことは別途未証明。

## 新規の隔離検証

## 退職・旧自己申請の追加検証（今回）

同じ2modeの既router fixtureへ、次の境界だけを追加した。製品SQL、製品UI、Auth/RLSは変更していない。

- 導入前metadata pendingの申請者を正規approval assigneeにもした場合、自己承認は42501で拒否する。ID・snapshot・pending状態は保持され、先行の独立reviewer承認probeで同ID承認成功を確認している。一括取消・再申請は不要。
- 管理写真の全除外requestをprepare→submitした後、workers.statusだけ退職へ更新できる。資格原本は不変。退職後approveは40001、pending内容も不変。一方、別の正規reviewerの理由付きrejectは成功する。Storageの旧写真参照保護を維持する。
- 合成schemaへ明示したworker外部キーON DELETE CASCADE経由でも、資格guardが42501で拒否する。親workerと資格原本はrollbackされる。この結果は「退職status更新は可、物理削除は不可」の分離を証明し、本番全FKの形を証明しない。

Node/PGlite実行は2modeとも成功。既成功範囲の全除外prepare→submit→独立approve→正式写真null/空配列と、今回の退職・旧pending条件は同一fixtureで共存する。ローカルFlutterは未起動、実iPhone未確認。

### 本番HOLDを解除するためにrootへ渡す最小条件

1. 本番catalogのみで候補の許可済MD5/full属性・ALL row guard対象・既retirement status writer・worker/company/Auth FK cascade・依存関数を照合し原本を保護する。退職statusは資格本体UPDATE/DELETEを伴わないことを確認する。worker等の物理削除は本修正では許可しない。
2. 管理者の保存写真除外だけを提供範囲とし、旧Release/RESTによる直接正式写真UPDATEはguardで拒否する。現PR1313画面は既申請routeへ接続済みなので、旧repositoryのthrow-only PRは新設しない。管理新upload・metadata変更・登録本体DELETEを成功する機能として提供しない。もし運用上必須の既writerが実際に残っていれば、そのwriterに限って正規承認代替を先に作る。未発見のwriterまで全置換を要求する抽象HOLDにしない。
3. 原本backup・writer停止/実行中排出・利用開始後queue/historyを残す復旧を整え、既admin候補＋baseline＋readinessを一括導入する。申請者本人が承認者の既pendingはID保持のまま別の正規reviewerで扱う。退職済み管理写真pendingは原本を維持して理由付きrejectできる。
4. 専用readinessがONの実応答を確認してからRelease flagを有効にする。同じ資格・同じrequest IDで写真1枚除外／全除外の申請→別正規reviewer承認→一覧再読込を実機確認する。自己承認制限のため独立reviewer不在なら、権限緩和で迂回しない。

登録本体削除は現承認APIに操作が存在しないため別未完。将来の最小設計は既qualification_submissionsの固定ID・previous snapshot・独立review・監査結果を再利用し、写真除外とは別operationとしてprepare/submit/reviewを定義し、承認後も原本・共有写真参照と監査を保持すること。現admin_saved_photosへ空配列を送ることは登録本体のDELETEにはならない。新APIやschemaを今回推測実装していない。
