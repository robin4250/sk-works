# 共通手当の給与適用月を管理画面から登録する

PR #1281 の適用月履歴・限定再計算RPCに依存するclient候補。前段のSQLを再実装せず、社内共通手当の管理画面へ「給与への適用月」を追加する。

追加した共通手当を保存した後、給与形態と現在月以降の適用月を選び、確認画面で「適用する」を押す。未保存の編集内容は含まない。給与形態の初期値は画面の初期表示と同じ時給、保存後は保存した形態に合わせる。APIには読取時の会社設定version/sourceとtimeline versionを渡し、同じ会社・request・給与形態・月・publication versionを持つreceiptだけを採用する。保存済み適用月を直近5件表示する。

結果不明時は新しいrequestを作らず、同じrequest ID・完全payloadで「適用結果を確認」する。現在の画面で未解決のrequestがある間は共通設定の編集を止める。serverは同requestをreceiptから返し、再計算を繰り返さない。request/receiptはserverに保存されるが、このclient候補の未解決requestは画面メモリ上のみで、アプリ終了後に同requestを自動再送しない。再起動後は適用月の保存済み履歴を再読取する。

RPCは元tokenに固定し、ログアウト・同token再ログイン・token変更を検出した旧応答を採用しない。会社切替・背景移動後の旧応答も表示しない。閲覧者には適用ボタンを出さず、書込の認可・確定保護・CASは前段serverでも確認する。旧serverでpublication APIがない場合は準備状況の確認を表示し、成功扱いにしない。

テストは実Supabase SDKの合成HTTP応答でtoken固定・同token ABA・receipt不一致を検証し、widgetで月選択・確認前に送信しないこと・結果不明時の同request照合・viewer・遅い応答の破棄を確認する。既存共通設定の保存/固定フッター回帰も対象。実JWT・本番配備・実機利用確認ではない。

本番では既存identity/common基盤・前段2候補のSQL、activation開始月と復旧/互換条件の確認が必要。本候補だけで実データが更新されたとは扱わない。個別金額overrideと過去月の承認付き訂正は別工程。
