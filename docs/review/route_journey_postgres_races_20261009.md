# Route journey capture targeted PostgreSQL races

This harness runs only against localhost and the exact disposable database `sko_route_capture_race_fixture`. It refuses remote URLs and other database names before connecting. GitHub CI creates a PostgreSQL 16 service with synthetic prerequisites, applies the actual staged route capture migration, and uses independent clients with observed `pg_stat_activity` Lock barriers. No production database, account, feature flag or registered data is accessed.

The schedules cover simultaneous identical UUID commands (one immutable raw row; the 23505 loser recovers its own exact UUID/payload), clock-out versus source capture in both lock orders, saved-report link versus capture, and committed OFF while save waits on its source. Clock-out writes in this small fixture explicitly acquire the actual source lock; this is a boundary test and does not execute every historical attendance migration or the whole production clock-out flow. Report linking may run before an uncommitted capture becomes visible; repeating the same saved report links that committed capture without modifying its raw fields.

The upload schedule deliberately waits at the fixture storage primary-key index after the ON policy decision, then commits OFF. An upload already admitted while ON can finish after OFF. A subsequent capture save must be denied; the uploaded object is preserved instead of being deleted after an uncertain result. This is not proof that turning OFF cancels in-flight uploads. Retention, abandoned-upload cleanup and account deletion/archive integration remain unfinished and require separate design before activation.

Local checks: JavaScript syntax and the existing actual-migration PGlite capture/storage fixture. Local real PostgreSQL cannot run under the available root-only UID mapping; no root-euid shim is used, and local real-PG success is not claimed. CI PostgreSQL results must be recorded in the PR after execution.

Both rollout gates stay OFF. Production migration application, complete historical-chain verification, real physical-iPhone operation, every destructive race combination, and new-bucket retention/deletion behavior remain unverified. CI success here does not authorize production ON or device publication.
