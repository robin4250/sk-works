# 個別給与設定の共通手当読込互換性

## 確認した原因

同じ会社・同じ月の読取専用比較で、問題の対象だけ共通項目4件のうち2件が `source=confirmed_checkout_receipt` で、`quantity_month` を持たない形式だった。他の5対象は各2件の通常publicationだけで、対象月の欠落はなかった。会社とworker設定の紐付け、給与種別、対象月のdraft状態に異常は見つからなかった。条件itemsが空の対象は他にも存在するため、空配列は障害原因としない。

既存parserは全共通項目に `quantity_month == response.month` を要求する。そのためこの正規receipt形式だけで読込全体が失敗し、共通手当表示と単位別追加の準備を完了できなかった。対象名やUUIDによる画面の特別扱いは追加しない。

比較は管理接続のREAD ONLY transaction内で、既存本人リンクのsubを一時設定しSTABLE読取関数を観測したもの。実際の端末JWT、PostgREST、RLS経由の成功を証明するものではない。最初のsubなし観測に対する `paid hours unavailable` は調査接続の認証文脈欠落であり、端末の原因とは扱わない。設定・給与・認証情報・RLS・関数・原本の書込は行っていない。実名・実UUID・給与値はこの公開記録に含めない。

## 修正範囲

通常の明示対象月検査は維持する。対象月のkeyが存在しない場合に限り、既存確定receipt形式・company_common由来・正整数のregistration版・1〜31件の重複のない実在する日付が全て要求月に属することを照合する。明示null/別月、不正日付、通常publicationの欠落、負値、重複IDは拒否する。

表示項目、単価、数量、金額を再計算・補完しない。元のsource JSONを変更せず保持するので、時間保存に使う既存expected-source CASも維持する。新しい認可やreceipt署名検証を実装したとの主張ではなく、既存認可RPCの応答互換性の修正である。書込RPC名・引数・会社/worker選択・認証・SQLは変更しない。

## 検証段階

新27試験は混在receipt、通常publication、21拒否境界、重複ID、閏年/月境界、実SDK loopbackの会社/worker/月引数と既存応答形式を対象にする。元repository試験も専用CIで実行する。ローカルFlutterがないため、CI結果が得られるまでは成功扱いしない。

二重追加/登録ボタンは別PR1559の親footer一本化で対応する。読込失敗時に未検証の日/時間項目を無理に追加可能にしない。今回の互換修正と合わせたUI・CI・main反映、本番端末での比較、役職手当振替の計算と保存後明細照合は別の未完了段階である。既存給与データ削除・初期化・本番再計算はしない。
