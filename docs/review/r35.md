Read-only review, 2026-10-17 JST. No login, account creation/linking, provider,
credential, role, company, database or native signing setting was changed.

## Reuse, do not rebuild

Current main exposes the existing Google and phone-password entry through
main.dart -> app_v2.dart -> SupabaseAuthGate -> SecureAuthPage. No Apple login
entry is wired. Bounded earlier source/history/PR searches did not establish a
working historical Apple product implementation; this is not proof of absence.

PR1167's merged identity_link_sdk_contract_test.dart already verifies the pinned
SDK's authenticated identity-authorize/JWT/PKCE/callback and collision-no-fallback
contract. PR1180 exact4edb54e2ae259a7a05350d1d7e1e20bba8dc26d7 already supplies
PanelNineProbe and tests for stable UID, original identity retention, added Apple,
unchanged company-role reads and late actor switches. All eight exact-head CI
runs succeeded, including dedicated38990321366, Flutter38990321338 and
iOS38990321440. These are synthetic SDK/read-only checks, not real Apple linking.
Reuse these; a second preservation module is unnecessary.

## Two different actions

| Action | Client responsibility | Server/provider responsibility |
|---|---|---|
| Add Apple to a signed-in existing account | Existing-user getUser + identities/company-role snapshot; fresh approved operation reauthentication; authenticated linkIdentity(apple); original UID and identities/company roles verified after callback | Apple enabled and correctly configured; manual linking enabled; collision rejects; fresh actor/session/operation-bound proof available |
| Log in again with previously linked Apple | Existing OAuth/PKCE callback and guarded navigation pattern; server-validated identity/company reads after callback | Provider verifies Apple; the linked identity resolves to the original UID |

Anonymous Apple sign-in is not an existing-account linking substitute. Normal
OAuth may create another user when the selected Apple identity is unlinked.
Names, matching email and Apple private-relay email are not safe UID merge keys.
No role reassignment, user deletion/merge or signup fallback is proposed.

## Smallest platform choice and unverified prerequisites

The browser OAuth option can reuse the existing exact native return URI
com.skworks.sko://login-callback/ and supabase_flutter PKCE/app_links flow.
tool/prepare_ios.sh already preserves that scheme and sets
FlutterDeepLinkingEnabled=false. It has no native Sign in with Apple capability;
pubspec.yaml has no native Apple sign-in package. Reusing browser OAuth avoids
silently inventing a native token/nonce/capability implementation, but it is only a
candidate architecture, not a verified recommendation for a signed device.

Before enabling a browser entry, privately verify the Supabase Apple provider,
Apple Services ID linked to the correct App ID/Team, allowed Apple website domain
and HTTPS callback https://ztktgquxvcxcjxtluspu.supabase.co/auth/v1/callback,
the existing app return URI allowlist and signing secret validity. Apple OAuth
secrets require rotation within six months; secrets and private signing keys must
never enter the app, repository, issue or logs. None of these live settings was
verified in this review and no setting was changed.

Native ID-token flow is a different alternative: Apple capability and signed
profile entitlement, cryptographic raw nonce/SHA256 binding, native package,
correct token audience and authenticated linkIdentityWithIdToken. Existing Google
callback success does not verify these requirements. Do not add either platform
implementation merely because the other has prerequisites.

Google-only fresh server reauthentication remains unresolved in the staged
password-only proof contract. An app boolean, Face ID alone or the secondary
password must not masquerade as that server proof. Keep Apple-add unconnected
until it is resolved; do not force current users out or block their working login.

## Completion evidence still needed

Use an isolated Apple/provider environment and original synthetic Google account:
link Apple, retain original UID/company/role/identities, restart, logout, Apple
relogin and Google relogin. Test collision/wrong Apple/cancel/background/late
callback/account switch without creating a second production account or signing
out a newer actor. UI success must follow server-validated completion, never the
browser-launch return. Same-token PanelNineProbe may reject legitimate refresh;
it is preservation evidence, not completion authorization or a server proof.

Only after concrete source, isolated checks, provider readiness and explicit
production-setting approval should an entry be exposed. This work does not make
Apple/phone account linking or the first-use two-auth policy complete.
