# Authenticated-account invitation v2: candidate scope

**Review-only source, default OFF. Not installed or ready for employee distribution.**
Main inspected: `214bf2e3875782ba0e66971d047746ec1f4fcba3` (PR #1303 merged).
No production Auth, hook, RLS, provider, account or invitation was changed.

## Decision

Develop an authenticated-account alternative first. A manager still preregisters the employee with name/phone and displays a QR. The QR contains a 256-bit random bearer token, invite reference and generation, never an Auth password. The recipient first signs in using their own established identity, explicitly confirms the displayed account, then redeems the invitation atomically. The server uses the verified JWT UID and a live matching `auth.sessions` row, not a claimed UID or matching phone/email text.

This alternative does not solve the separate unauthenticated, phone/password-only first-login requirement. Phone remains OFF. Apple provider remains an independent prerequisite. Do not switch an existing owner account, invent an email identity, or present this limited path as the original phone QR flow being complete.

The rejected alternative was creating a new password bridge and storing it encrypted. That needs new key lifecycle, enrollment/crash cleanup, password-reset/approval race protections and recovery rules. Resetting an existing ordinary account's password during redemption could damage its established login. The selected path never provisions, updates or deletes an Auth identity and never changes its JWT role globally.

## Implemented candidate SQL slice

`docs/candidates/employee_authenticated_invite_v2.sql.review-only` is not a migration and is never loaded by the app automatically. It adds a private per-company flag with `enabled=false`, a private invitation ledger, authenticated issue/redeem/cancel RPCs and an internal proof predicate used by the separate profile-gate candidate. It does not grant access to the private tables.

Issuance is restricted to an existing owner/admin and an unlinked preregistered employee in that same company. This initial slice is viewer-only; do not route the current manager/approval-assignee options to it or silently discard them. Existing worker/UID or prior product registration requires review instead of reassignment. The supplied issue operation ID is idempotent only for the same actor/token hash. New issuance advances a generation under the worker/ledger locks. The token plaintext is never persisted; only a 32-byte SHA-256 digest is stored. Name/phone are snapshotted; a later changed worker snapshot invalidates redemption.

Redemption creates a real existing-schema invitation in `profile_pending` while leaving `password_changed_at=NULL`. The original profile function rejects that row. The separately reviewed profile-gate candidate now accepts the bound live proof in fixtures, without changing either credential marker. This is **not a usable onboarding completion**: app, capability, approval and Storage integration remain outstanding. Target-company membership and the worker's user link remain absent. Existing ordinary accounts with an existing registration or target-company membership are rejected without changing either.

The worker lock precedes the ledger lock in issue/reissue/redeem/cancel. The same actor, actual session and operation ID can retry for the original bounded receipt only. A different actor, session, operation or generation is refused. The receipt contains protocol/operation/invite/company/worker IDs only; it contains no Auth token, password or new session. Consequently a lost network response cannot issue a second Auth session. SQL rollback undoes both the product row and ledger consumption together.

Cancellation also cancels the bound pending product invitation. An already-approved registration cannot be cancelled by this RPC. The proof checks the bound UID, session, company, worker, pending state, invitation expiry, ledger expiry, rollout and session revocation. The private registry remains durable; disabling rollout does not delete identities or records. Existing Google, email, Apple and Face ID behavior is not modified.

## Evidence and limits

The PGlite test loads the actual main employee-invite foundation SQL as a fixture, then executes the candidate RPCs under `authenticated`, using synthetic IDs and worker records. It proves default-OFF refusal, normal issuance, issuance receipt retry, changed-hash refusal, generation rejection, wrong-token rejection, real product-invite insertion, same-operation receipt retry, different operation/UID refusal, no membership/worker link before approval, unchanged Auth password hashes, session-revocation refusal, cancellation, expiration and approved-registration preservation. It also verifies the private ledger has no authenticated SELECT grant.

This is one embedded Postgres connection. It does not prove concurrent connections, GoTrue, JWT validation by PostgREST, actual owner Google/Face ID, phone login, Apple callbacks, approval-function integration, service-role Edge caller paths, Storage or UI. The account-access dependency is an explicitly simplified fixture stub. Freshness of the bound Auth session does not by itself prove a recent reauthentication ceremony.

PR #1303's actual GoTrue proof established that the hook can see the live real session and that the isolated restricted-role lifecycle can work. That proof is reusable for the separate new-identity/unauthenticated protocol, but it is not copied into this authenticated-account protocol or described as production proof.

Required before making this usable: current deployed profile/approval source capture and validation of the candidate, app capability/issuer/scanner/confirmation/redemption wiring, old-client rejection on explicitly opted-in companies, requested-role support or explicit viewer-only UI, actual PostgREST/GoTrue and concurrency fixtures, sensitive graph/Storage audit, rollback and distribution review. No production enablement should occur from this candidate.

Official reference checked: <https://supabase.com/docs/guides/auth/auth-hooks/custom-access-token-hook> (the hook runs before token issuance and receives actual user/session claims). The changelog markdown endpoint could not be fetched through web-open; no changelog compatibility conclusion was inferred.

## Profile-gate integration checkpoint

`docs/candidates/employee_authenticated_invite_v2_profile_gate.sql.review-only` accepts only the captured profile body MD5 `3e0b34238e7d84abebdbd95593b64949` or the reviewed photo-retention body MD5 `3e5e7b7c799109c85d22ca4ce2a74d66`, with the expected owner/ACL/search path/function shape. It also checks the exact private proof body hash `e941ec1190ddf66dab9131e22b779138`, its restricted execution privileges, and the ledger RLS/client ACL. It refuses drift and refuses blind repeat application.

The patch replaces exactly one predicate: a ledger-bound product invitation requires the live same-UID/same-session proof; an ordinary legacy invitation retains the original password-change-or-identity-verification condition. A v2 row cannot bypass session checks merely by having either old marker populated. The full remainder of the existing function definition is reused byte-for-byte, preserving OID, EXECUTE ACL, owner, photo pause, required fields, notification code and existing status rules. It does not populate `password_changed_at` or `identity_verified_at`. It does not add a membership or worker link.

A dedicated fixture loads both captured profile variants and executes actual RPC calls against the product invitation created by candidate redemption. **35 checks pass**: the old function initially refuses that row; the new gate allows profile submission with both credential markers NULL; legacy password and identity proof still work; approved accounts remain unmodifiable; wrong-session and expired/revoked/cancelled proof fail; legacy markers cannot bypass a v2 proof; paused uploads and required fields still fail; photo-retention variant preserves all three existing references; source/hash/privilege drift and blind repeat patch are rejected. The original unretained variant retains its existing photo behavior; this predicate patch is not a replacement for the independent photo-retention fix.

This connects the real profile-save SQL boundary in the fixture, not only a helper. The photo capability RPC, no-photo wrapper contract, approval function and Storage are still separate integration/review requirements. It does not prove the whole onboarding UI or a live deployment. A live matching session is checked, but a fresh reauthentication ceremony is not independently proven. No product UI files were changed.

## Approval-gate integration checkpoint (2026-10-20 evening)

`employee_authenticated_invite_v2_approval_gate.sql.review-only` is a separate, default-OFF-dependent source candidate. It accepts only the read-only captured production approval body MD5 `43a11acbc88d289bb17eec739b371f2a`, its exact owner/ACL/security/search-path contract, the unchanged v2 proof body and the canonical account-access predicate body MD5 `aeca25db212c043c472334026bd98724`. It inserts one call into the captured approval before the existing product-invitation row lock. The rest of the approval function is retained byte-for-byte, including reviewer/role checks, notifications, updates and assignee-limit handling. The patch preserves the original function OID, owner and EXECUTE privileges and refuses blind repeat installation. Unknown default EXECUTE grants on the new private helper roll back installation.

The private gate returns immediately for a legacy invitation with no v2 ledger binding. A v2 invitation requires an authorized reviewer with a live actual session; the original reviewer permission logic runs again unchanged. It then locks rollout in shared mode, followed by worker, v2 ledger and product invite in the same order as issue/redeem/cancel. It requires an unexpired, redeemed, enabled binding; a live bound employee session; an unchanged employee snapshot and no existing worker user link; no account-deletion restriction, Auth ban, soft deletion or anonymous identity; and the initial viewer-only role without assignee escalation. It does not compare the reviewer UID to the employee proof's `auth.uid()` and never impersonates the employee or fabricates JWT claims in production.

The initial approval slice deliberately refuses an employee account with **any existing company membership**, including ownership of a different company. The captured original approval writes global `user_profiles` fields. Silently approving such an account could therefore overwrite its established profile even without changing its Auth identity or other company role. Existing-company transfers and owner accounts require an explicit separate flow. This is a conservative restriction, not proof that all established-account enrollment cases are complete. Earlier redemption can create a pending row for such an account; this approval candidate stops it before membership/worker/global-profile writes. An eventual capability/UI must explain that boundary before redemption.

A new isolated PGlite fixture executes the actual captured approval after the existing v2 issue → redemption → retained profile-save path. **50 checks pass**: ordinary successful v2 approval produces the real membership and worker link without filling either password/identity marker; cancellation, expiry of either ledger or product, disabled rollout, worker drift, role escalation, deleted/expired employee session, wrong reviewer session, outsider/self-review, existing membership (including other-company owner), banned/deleted/anonymous subject and deletion restriction are refused; notifications failing after writes cause the whole statement to roll back. Legacy approval succeeds with the captured original behavior. Existing passwords and original function metadata remain unchanged. Source drift, ACL drift, unknown default grants and duplicate patch application are rejected.

All users, claims, sessions and company rows in that fixture are synthetic. This is not actual PostgREST/GoTrue token validation, multi-connection cancellation/approval concurrency, Storage proof or mobile UI completion. The helper's employee/reviewer session checks do not independently establish a recent reauthentication ceremony. No production function, provider, account, membership or invitation was modified. Approval integration no longer consists only of a plan, but the remaining capability/no-photo/photo/Storage/issuer/scanner/UI and real HTTP/JWT requirements still block distribution.
