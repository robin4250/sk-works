# 車両出勤・メーター・整備通知の確定仕様と実装差分

基準 main: `a2a0ad26cebfbcc39ec99fe49f8b78d4ceb6c202`。この変更は純粋な判定モデル・テスト・設計書のみ。DB、認証、RLS、画面、本番通知には未接続。

## 確定した利用フロー

1. 出勤時、運転手が車両を選ぶ。同じ車両は同時に一人だけ利用できる。
2. 登録成功後、指定された車両担当者へ「〇〇さんが［車両ナンバー］の利用を開始しました」。失敗した出勤では送らない。
3. 運転手のみメーター写真の読取結果を確認・手修正して登録する。現場の日報入力者が別人でも、その人が運転手の数値を代入力しない。日報完成を待たず運転手の入力を紐付けられる必要がある。
4. 車両の利用終了時刻は運転手の退勤時刻。代理退勤も対象となる運転手の出勤IDへ結ぶ。日報登録時刻を利用終了にしない。
5. 日報に前回・今回のメーター値と、その勤務の走行距離を保存する。車両登録の現在値を後から変えても、過去日報の距離は変わらない。
6. 数値が減少した場合、差分距離を推測しない。管理者への基準値変更通知と、運転手へのその日の走行距離の手入力誘導。車両の現在値は今回値へ変更する。前回値は履歴として残す。メーター交換の社内情報は別管理。
7. オイル交換・定期点検は「3,000kmごと」等の繰返し間隔。指定する社内担当者は1〜3人。外部メール送信先も設定可能。一方向のサポート通知で、返信・整備完了入力を必須にしない。
8. 通知内容は会社名・担当者・担当者電話・車両保管場所・車両ナンバー・車種・前回値・今回値。送信元は設定済みSKOサポートメールを使用し、未確認のアドレスを作らない。

## DB実装時に必須の原子性と権限

- 出勤確定と車両利用claimを同一トランザクションにする。claimは会社・車両・driver worker・source_clock_in_id・利用開始時刻・終了時刻を保持。終了NULLの車両に一意制約を置き、並行する出勤の片方だけ成功させる。失敗で勤怠だけ保存しない。
- 利用終了は対応する退勤のトランザクション内。同じ出勤への重複退勤は既存制約を維持。前夜勤務、月跨ぎ、同じ日の次の出勤を混同しない。
- メーター保存は車両行と利用claimをロックし、company一致、現在の会員資格・account access guard、本人workerとdriver一致、日報と勤務の一致を検証。車両管理者の権限で一般社員の報告値を直接変更する抜け道を作らない。承認済み変更は専用の既存承認経路で記録する。
- 利用開始時点の基準値と保存時の前回値は用途を分ける。出勤時のsnapshotから当日差分を計算し、コミット時はvehicle version/最新meter eventを確認。遅れて入力する旧勤務が、後続勤務の現在値を巻き戻さない。旧勤務は当該勤務の履歴だけ修正し、承認・再計算が必要なら別経路へ誘導。
- `reading_event_id`等の一意な操作IDで再送・再保存を冪等にする。同じIDの別数値は拒否し、同じ内容の再送は既存snapshotを返す。現在値を読み直して同じ日報の差分を0にしない。
- 基準値減少は履歴eventを保存し、manual distanceがない状態を明示する。新しいmaintenance epochを作成し、旧epochの通知を再発行しない。次回間隔のoriginはreset時の現在値として明示保存する。
- 整備ruleは車両・種類・origin・interval・epochを保持。crossingのキーはvehicle/rule/epoch/ordinalの組を一意制約にする。間隔・origin変更も新epochとして旧通知を保持。複数閾値を一度に超えた場合、各閾値のeventを記録し、同一送信内でまとめられる。返信待ちにはしない。
- 通知/outboxは実データのcommitと同時に一意キー付きで作成し、配信失敗によって出勤を失敗させない。worker start通知は利用claim ID、基準値変更はmeter event ID、整備はcrossing IDで重複排除する。
- 社内宛は同一会社の指定担当者のみ。外部宛は管理者が明示登録した宛先のみ。外部メールはサーバーから配送し、送信元の所有確認・設定・プロバイダー資格情報を確認する。アプリに送信secretを入れない。配送retryと配送履歴を保持し、画面には未送信・失敗を区別する。
- 通知本文の会社・車両・担当者情報と前回／今回値はevent発生時snapshot。後から車両を編集して別車両の情報になることを防ぐ。
