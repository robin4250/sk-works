# Scanner key custody foundation — OFF and unexposed

This supplies a real native signing primitive for the existing HTTPS scanner
registration contract. It does not expose a registration screen/route, call the
registration endpoint, change server authorization, or enable QR. App registration
controller/UI remains incomplete until this primitive and its lifecycle are
verified. Employee-invitation scanning is unrelated and is not reused.

The fixed native service stores an Ed25519 CryptoKit key as a generic-password
Keychain item under SHA256(domain + verified actor + company + device). Dart
performs exact-token GoTrue getUser validation and rejects Auth history, errors,
completion, disposal and lifecycle invalidation before/after native operations.
Company/device are local scope selectors, not authorization; server membership,
manager permission, live SID, QR gate and dedicated second password remain
mandatory. No bearer, password or raw private key crosses the native channel.
The returned handle/public SPKI/signature provides no registration attestation.

Keychain creation requires WhenPasscodeSetThisDeviceOnly, no synchronization,
and userPresence access control. Each native operation starts a fresh
LAContext/deviceOwnerAuthentication with zero Touch ID reuse duration. No
unprotected fallback, key replacement, deletion or export method is provided.
Existing-item errors never cause key regeneration. The domain-separated
registration payload is assembled natively and rejects scope/SID/key/schema/
time drift. Background and expiry cancel pending operations; monotonic checks
also reject late synchronous completion. Unknown local creation outcomes are
reconciled by another explicit prepare of the same scope, never replacement.

CryptoKit Ed25519 raw key bytes exist inside native process memory and Keychain;
this is not a Secure Enclave key or a claim of non-exportability against a
compromised native process. `userPresence` allows system biometry or device
passcode, not necessarily a specific biometric person. Owner/company identity
and server authorization are separate. No keychain sharing entitlement is added.
Both Dart compile-time preparation and native Info.plist flags default false;
prepare_ios.sh explicitly sets the native flag false even on reused projects.
No real user key is generated by this change or its disposable tests.

The dedicated native fixture checks the actual RFC8032 CryptoKit vector and
canonical server payload, then calls actual Security.framework with a unique
synthetic scope. A hosted process may lack Keychain entitlements or a passcode:
that limitation is reported and no successful storage/signing is inferred.
If protected insertion succeeds, no-UI retrieval and signing must fail. Tests
never fake successful local user presence. iOS API typechecking and the normal
unsigned Release build are distinct from signed iPhone presence/restart tests.
The Flutter tests compose the actual Supabase SDK/MockClient with a mocked
MethodChannel; they prove guard/argument behavior, not native key custody.

Remaining: signed iPhone passcode/Face ID/cancel/background/restart/key-retention
checks, end-to-end native signature acceptance by actual GoTrue/PostgreSQL,
secure non-secret pending-operation journal, registration controller/UI using
challenge/proof/PoP/result and proof_result without blind retry, hosted admission/
transport, least-privilege pool, restore/retention policy and canonical attendance
mode/writer. No production DB, grants, routes, migration, deployment, activation
or individual-document exemption setting is changed.
