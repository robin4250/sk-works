# Collector owner reauthentication — independent OFF analysis

The existing collector read uses operation `master.security_collector.read` and exact target `{"scope":"decoy_collector"}` with an actor/session/target-bound, one-use server proof. The current issuer verifies a primary login password. Existing Google-only ownership does not establish that such a password exists, and a local Face ID success, an existing JWT or its refresh, a secondary password, or a provider email cannot satisfy that proof. The collector gate remains OFF; ordinary Google and Face ID login remain unchanged.

The existing `google_primary_verifier.mjs` is an internal verifier: it verifies a genuine Google RS256 token against a trusted key, matching existing immutable Google subject, nonce, audience, fresh `auth_time`, original GoTrue actor/SID and a server challenge. It returns internal evidence, not a collector operation proof or Auth session. The added isolated test verifies that its existing contract accepts the exact collector operation and target, rejects stale authentication and session mismatch, and consumes its synthetic challenge once. No network, real user, password, server credential or deployed endpoint is used.

Required before a real Google route: a supported iPhone acquisition method that reliably sends a server nonce and proves fresh Google `auth_time`; a securely generated, short-lived, single-use challenge fixed to actor, live session, collector operation and exact target; fixed-origin key resolution; transactional consumption with identity, session, Master role, access barriers and deletion rechecked; and the existing service-only proof issuer called with those exact server-verified bindings. Revalidate exact bearer and actor/session through the full flow and reject A→B→A client history. Challenge consumption and proof issuance need defined crash/retry/recovery behavior and native concurrent tests. A newly minted token, account selection, Google consent or JWT `iat` alone is not fresh authentication. Existing provider subjects must be matched directly, never by email.

Apple credential preparation serves account linking and is not an existing collector proof. Its reviewed nonce and identity binding must not be reused as proof of fresh owner reauthentication without a separate Apple subject/session/operation binding and a real supported authentication guarantee. Face ID can locally unlock a protected private key but a client-reported biometric result is not server-verifiable. Device-bound asymmetric proof would require the currently unfinished trusted-key enrollment, cryptographic verification, revocation, lost-device recovery and actual device tests before use. OAuth-only secondary-password recovery is a separate process; do not substitute the second password into the primary proof contract or introduce a new per-action attendance password prompt.

Real GoTrue plus provider/device tests, account-preserving operation-proof issuance, client acquisition, recovery and production restore are all unimplemented. No grant, login, device enrollment, database update, production activation or credential reset is included. Tests of this offline boundary do not establish production readiness.
