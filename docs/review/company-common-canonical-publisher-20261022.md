# Canonical v2 common payroll publication — review candidate

No production execution. This is a proposed versioned API over the **existing** canonical publication, activation and receipt storage. It does not add a permanent future-policy or alternate legacy-publication calculation path. It is not ready for production until independent/native/concurrency/real-token/UI and deployment checks are complete.

## Default-off atomic code installation

The proposed deployment set is exactly the canonical snapshot, resolver and publisher review units, on top of the exact existing canonical bridge/effective baseline. Compose the units in that order inside **one** transaction by removing their outer `begin;`/`commit;` wrappers. The publisher's dependency guards pin the reviewed snapshot/helper/resolver/augmenter/common-state source hashes and expected ownership, ACL, argument, language and execution attributes; the resolver guards the existing pre-change functions. Root must remain the sole DDL writer. The fixture proves an intentionally failed resolver guard rolls back the earlier snapshot schema, and a successful combined installation leaves all observed settings, salary, activation and publication data unchanged. Do not install the earlier standalone legacy/future prototypes as a deployment dependency.

The newly installed capability probe returns integer 2 but does not enable payroll. No activation or publication is inserted during installation. The UI must require deployed v2 capability and keep its new flow off until that capability is observed. Activation is only changed by an explicitly approved administrator publish command; install success is not that approval. Existing exact v1 receipts still replay normally, and old v1 publications without named positive legacy slots keep their old behavior. New v1 publishes for companies with positive legacy slots are refused with a v2-contract requirement so they cannot drop legacy items from the next canonical snapshot.

## Request/response contract

Preview RPC: `preview_company_common_payroll_v2` takes existing `p_company_id`, `p_payroll_type`, `p_starts_on`, `p_common_version`, `p_common_source`, `p_timeline_version`, plus `p_legacy_quantities` and `p_individual_reconciliation`. Quantities are the exact snapshot identity/generation/display-unit decisions with basis `attendance_selected_distinct_dates` and one current-name alias. The reconciliation value is `inherit_absent_or_same_rate_otherwise_unresolved`; this is a calculation policy, not a transport retry mode.

Preview returns `contract_version:2`, `ready`, opaque `preview_token`, `command_base`, `activation_required`, `target_count`, `excluded_count`, `unresolved_count`, `scopes`, `next_effective_boundary`, `items`, and the existing v1 `timeline`. Scopes include worker/month/status and safe reason/source classification, with hashes of current worker settings, attendance and salary originals. Manual and finalized records are excluded. Existing current and later salary scopes are considered until the next already-effective boundary. At most 100 scopes and a reviewed 12-month horizon are accepted. Unknown or conflicting legacy selections and unresolved individual/common hour quantities prevent publishing.

Publish RPC: `publish_company_common_payroll_v2` takes the preview's eight fields plus `p_request_id`, `p_preview_token`, and explicit `p_approve_activation`. The command persisted by the client and sent as `p_expected_command` to receipt lookup is that **entire exact p_* parameter map**, including those final three fields.

Publish uses the original company writer ordering and canonical per-scope locks. It recomputes the preview after waits and requires the same token. First activation approval, immutable canonical publication, target recalculation, original-input/excluded-salary preservation checks, exact common-item readback and receipt insertion are in one transaction. Same actor/request/payload returns an existing receipt **before** new source/timeline CAS, including after an unknown commit; a different payload is refused. Do not generate a new request ID automatically after a network error.

The result has `contract_version:2`, company/request/publication identity, start/type, `recalculated_scopes`, `excluded_scopes`, `unresolved_scopes`, `activation_changed`, `scopes` and the v1 `timeline`. Target scopes have readback status `verified`, or `no_salary_without_attendance` for a non-monthly scope with no salary and no attendance. Excluded scope records retain their exclusion status. A blocked or mismatched target readback rolls the entire publish back.

Read-only lookup RPC: `read_company_common_payroll_publish_receipt_v2(p_company_id,p_request_id,p_expected_command)` requires current admin authorization, the same actor and the exact command. It returns `{contract_version:2,found:false}` or `{contract_version:2,found:true,result:<stored publish result>}`. It never submits a publication. Missing receipt does not authorize automatic replay or a new request ID. The capability probe is `company_common_payroll_publication_v2_contract_version()` with no arguments.

## Isolated evidence and unfinished boundaries

The public fixture composes the three units atomically and exercises the public RPCs under fixture authenticated roles and synthetic claims. Synthetic and externally supplied private-rate inputs succeed without copying private input into git. It verifies default-off installation, explicit activation refusal, target/manual-exclusion counts, unresolved preview, stale-token refusal, atomic readback/receipt, same-payload retry, no duplicate receipts, changed-payload refusal, same-company different-admin receipt denial, manual originals and actual attendance edit recomputation. A synthetic trigger that mutates an excluded manual salary causes the whole activation/publication/payroll transaction to roll back.

These are disposable database tests, not real issued JWT/RLS/proxy endpoint or iPhone tests. Native PG17, concurrent finalization/settings/attendance/session changes and lost-COMMIT transport still need dedicated evidence. The fixture currently proves a current-month target and manual exclusion; complete future-scope/multi-type/100-scope bound and audit/printing rollout checks remain. Snapshot and publisher source hashes are not a substitute for transitive dependency review. No live financial amount or activation was changed.
