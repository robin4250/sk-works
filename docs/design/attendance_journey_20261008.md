# 外回り・会社出勤の勤務誘導

状態：PR #757でモデル・既存撮影画面・開始/終了RPC・原記録保持・移行を実装。本番DB反映と実機通し確認は未完了。

## 基本

一日の勤務開始・終了と、各訪問の開始・終了を分ける。すべての訪問は明示した出勤IDとサーバー勤務日に関連付ける。訪問終了だけでは勤務を閉じない。夜勤でも日付変更で勤務日を変えない。

## 誘導

1. 未出勤：『出勤する』→会社出勤／現場直行を選択。会社または現場、GPS＋写真など既存の確認方法を表示し確定。
2. 会社で出勤済み：『現場の作業を開始』。現場直行の場合は最初の訪問開始と勤務開始を同じ操作で関連付ける。
3. 訪問作業中：『この現場の作業を終了』→『次の現場へ』『会社へ戻る』『ここで退勤（直帰）』の次行動を選ぶ。訪問終了の写真・撮影位置はその訪問へ保存。
4. 次の現場：現場を選び『作業開始』。前の訪問が未終了なら確認を求め、推測した終了時刻で閉じない。
5. 帰社予定：帰社時に『会社で退勤』。帰社予定から直帰への変更も可。
6. 勤務終了：日報へ。対象勤務日・訪問履歴・出退勤写真・位置情報・車両距離を確認して途中保存／完成。日報完成とGPS退勤の状態を分ける。

主ボタンは現在状態に応じた次操作ひとつ。現場変更や予定変更は補助操作へ。画面には勤務開始場所、現在現場、勤務日を表示する。

## 後からまとめる

現地の写真・時刻・GPS取得記録を先に残し、後から日報に関連付けられる設計とする。オフライン保存・再送は実装と検証が必要。位置情報を取得していない過去の記録は手動登録であり、登録時の現在位置で過去GPSを補完しない。写真EXIFは補助情報として扱い同時GPS実測とは区別する。

まとめて出勤の既存承認フローは維持し、承認済み勤怠へ同じ勤務の訪問証拠を関連付ける。別勤務への推測割当、同じ勤務の二重計上を防ぐ。

## チーム・車両

班長の日報処理と班員本人のGPS確認は別の記録種別として扱う。班長の位置を班員本人の測位記録にしない。代理退勤の権限と対象勤務の明示、本人操作との重複防止は追加実装・検証対象。

車両は累積メーターと差分走行距離を区別する。移動時間の給与算入は会社設定に従い、出勤場所・直帰選択だけでは決めない。

## 履歴の復元（PR #757）

`AttendanceJourneySnapshot` は version 1 の記録形式を読み書きし、明示された会社・従業員・出勤IDと照合する。訪問・退勤が持つ元勤務日/出勤IDも検証し、`AttendanceJourney.restore` で開始・終了操作を順に再適用する。未終了訪問を補完せず、重複ID・時刻逆転・別従業員・未終了のままの次訪問/退勤を拒否する。時刻はタイムゾーン必須、勤務日は日付のまま保持し、GPSの欠落や代理記録の区別を変えない。

これは接続用の記録形式であり、現在の `route_journey_workspace` のレスポンスとは別。既存GPS写真記録を訪問開始/終了へ推測変換しない。呼び出し元は読み込み失敗を「訪問なし」にせず、サーバーで認可・勤務ロック・二重送信照合を行った記録だけを渡す必要がある。本番DB移行、保存RPC、画面接続、写真保持の依存解消、Release反映はこの変更には含まれない。機能フラグは変更しない。

## 開始・終了の保存接続（隔離検証中）

PR #757の続きで、既存撮影画面・再送ドラフト・Repositoryから開始/終了のRPCへ接続した。`route_journey_visit_workspace` が提供する実記録の状態で主ボタンを切り替え、作業中は対象現場を固定する。新RPCがまだ存在しないDBは従来の撮影記録へ戻す。旧version 1ドラフトを開始/終了へ変換しない。version 2ではアクションと開始記録IDも固定して照合する。

正式移行は `supabase/migrations/20261010132957_route_journey_visit_lifecycle.sql`。既存capture INSERTと訪問イベントINSERTを同一トランザクションにし、勤務元行のロック後に未終了訪問を検査する。途中終了では勤務を閉じず、未終了訪問があればclock_out INSERTを拒否する。再送は同じID・アクション・開始ID・元payloadの一致時だけ既存結果を返す。raw写真payloadは変更しない。参照写真の削除・上書きだけを後述のrestrictive policyで保護する。勤務日は既存出勤の値を使う。履歴の開始/終了表示時刻はサーバー受信時刻で、撮影時刻/GPS測定時刻は別の原記録として保持する。
