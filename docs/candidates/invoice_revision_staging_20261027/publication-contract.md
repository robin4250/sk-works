# 請求書訂正：切替え契約（未実装・本番適用禁止）

対象は現在のID・原本・署名・承認を保持した訂正。現状は下記すべてを保証できないため、旧版の遮断も新行の作成も発行もしない。

## 準備段階（外部通知なし、未発行）

1. 実セッションと有効なマスター本人・請求管理権限、対象会社・取引先・期間を固定。認証、会員権限と全計算入力のwriterに共通のロックを、既存経路に適合した同じ順序で獲得。認証取り消し・同時更新・未確認のロック参加者や定義driftは停止。
2. 元のinvoice全列、承認、監査、印影、既存注文請書等を変更せず、元IDと保存revisionの関連を記録。原本・添付類を削除できない保全と復旧の設計を別途完了する。
3. 元invoiceの直接SELECT、旧ID参照のSECURITY DEFINER経路、通知・Storage・外部取引先・他機能の書込まで旧版発行を遮断する。旧clientですでに読み込んだ内容や保存済みPDFは取り戻せず、端末停止と訂正通知の運用が別に必要。
4. 提案を同じtransactionで再計算し、全入力・元原本の指紋と一致しなければ停止。手当・残業・ルート・経費・調整・税を含めて検証する。隔離fixture成功だけを実額と扱わない。
5. 新旧関係を一意に登録し、既存の自動請求部分一意制約を維持した正規の新invoiceを新IDで生成する。旧版は自動請求のまま、同月の別行が請求として二重表示・集計されないことを旧clientも含めDB側で保証できない限り作成禁止。
6. 旧承認・旧印影を複製せず、新invoice固有の承認行を既存制度でpendingとして作成。承認者の実操作による新承認が必要。新行INSERTで採番や印影snapshotが自動実行されるため、対象のtriggerと副作用を関数/ACL/依存関係の現行catalogごと固定して事前照合。候補に必要な印影取得の正規要件は別途検証する。
7. 上記の全ステップと失敗時のrollback、同一リクエスト再試行は原子的に行い、新旧が両方発行可能な状態を作らない。権限切替、DB再起動、処理途中の例外、変更競合を検証する。

## 新承認・正式発行

- 新版の承認は正規の承認者本人が現行セッションで行う。旧承認をコピー、管理者が代理で捏造、システムが自動承認することは禁止。
- 承認後、入力・元原本・最新版ID・認証・通知方針を再照合し、正式版と旧版の関係・旧版発行不可・監査記録を同一transactionで確定する。失効時は再計算・再承認する。
- INSERT時の `private.invoice_approval_rows_trigger` と後日呼ばれる `public.enqueue_due_invoice_approval_notifications` は独立した通知経路。他にも直接enqueue/送信経路がある。ユーザーが明示していない外部通知を起こさず、新版を非公開のまま承認可能とする設計は未完成。triggerを無効化する、送信済みの扱いを偽造する、通知を削除する、承認や日付を偽装することは禁止。
- 送信、通知や共有の操作は別の明示的な指示の範囲だけで行う。すでに配布した旧PDFをサーバー側から撤回できない。

既存実計算fixtureと参照プレビュー、隔離GoTrueセッション、承認行holdの局所ロック、限定4関数の保護だけ。旧appや全privileged RPC、storage、採番、全trigger、全計算writer、親子insert、全社処理、正規新承認・復旧は未証明。試作・CI成功は本番切替え完了を意味しない。
