# 登録済み資格の変更・削除申請候補

基準 main: `3b08b17b9666e764a628e77e67b8f0005b668ca5`。本番・main未適用、端末未確認。

現行の資格区分は利用可能。本人が提出した資格証写真は `personal_qualification_submission` の既存承認台帳へ入り、承認後に写真へ反映する。写真の並び替え・削除申請と、資格そのものの編集・削除は別操作である。現行の `QualificationCloudPage._delete` は案内表示のみで、資格自体を削除しない。

この追加候補は既存の `qualification_admin_saved_photos_20261019.sql.review-only` と ordered-baseline patch が前提。承認台帳・単回write permit・正式行の変更ガードを再利用し、新しい並行承認台帳は作らない。メタデータは証明書番号・発行者・取得日・有効期限・備考だけを変更でき、会社・保有者・資格種類・写真は変えない。資格種類の変更と新規写真追加は別契約であり、この候補には含まない。

会社を明示し、現在の owner/admin または `can_manage_people` を持つ manager のみ申請できる。既存候補の独立承認を維持し、申請者本人を承認者にしない。承認者も同社の正規管理権限と既存承認権限が必要。匿名・一般社員・他社・失効セッション・利用不可アカウントは拒否する。承認時に申請者の現在の会社権限も再確認する。既存本人専用prepareを代理利用しない。

画面が確認した正式行全体とprepare時の行を一致させ、submit・approveでも同じsnapshotを照合する。正式行・会社所属・資格種類の行ロックと既存の資格別advisory lockを使用する。固定request IDを再利用し、別内容で同じIDを再送した場合は拒否する。承認前に正式データを変更しない。

資格削除の承認は同一トランザクションのpermit一回だけでDELETEする。元の資格全項目は申請台帳のpreviousと既存正式履歴へ残し、写真は既存photo historyに保存する。Storageオブジェクトを削除しない。直接DELETEと会社／従業員のcascadeを安易に許可しない。履歴を会社終了時に保全する運用と復旧手順が整うまで本番へ導入しない。

PGliteで管理者・manager・一般社員・他社・失効セッション、古い表示の拒否、固定ID再試行、自己承認拒否、正式変更前後、直接UPDATE/DELETE拒否、写真／正式履歴の保全を確認。PostgreSQL17 CI、同時処理、実GoTrue、実Storageバイト、UI接続、能力判定、通知、iPhone操作、導入／復旧ガードは独立して未完了である。CI用Auth／Storageは合成fixtureであり、本番の本人確認成功を意味しない。

現行ビルドの資格写真申請はそのまま保持する。既存申請をこの新しい管理申請へ変換・承認・却下しない。
