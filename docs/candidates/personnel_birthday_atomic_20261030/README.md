# DOB four-function atomic capsule — review only

This additive successor closes the previously uncomposed transaction boundary between the saved three-helper DOB candidate and the fourth canonical public-save no-op fix. It changes none of those four frozen install/recovery source files, their guards, original function bodies, Auth, RLS, grants or client code. No production SQL/deploy/activation is authorized or performed.

`node tool/security/personnel_birthday_atomic/build.mjs` checks the exact SHA-256 of all four source files. It removes only their unique outer BEGIN/COMMIT, retains each body/guard unchanged, and generates one outer transaction with a shared cooperative advisory lock. Install is three helpers/nullable column -> fourth public save. Reverse recovery is fourth public save -> three helpers. Before COMMIT a new guard checks all four final body hashes and owner/ACL/config/SECURITY DEFINER/volatility/strictness/leakproof/parallel/kind/return attributes, plus the retained nullable date column. No intermediate source is committed. Do not apply raw individual scripts first and then this capsule.

This follows the PostgreSQL17 [transaction contract](https://www.postgresql.org/docs/17/tutorial-transactions.html): one transaction publishes all committed changes together, and rollback cancels its changes. The Supabase skill and current [changelog](https://supabase.com/changelog) were reviewed; this isolated composition does not change Auth/API behavior, upgrade a server or address device/TLS rollout. Cooperative locking does not prevent arbitrary non-cooperating administrator DDL. Current full catalog/default ACL/dependency and serialized operational control still require deployment review.

The dedicated PostgreSQL17 test reuses only the immutable personnel fixture bootstrap, not the old successful34/30 test suites. It seeds an existing pending proposal, executes partial install/recovery in an open transaction, and queries function/column catalogs from an independent connection to require no partial publication. A forced middle failure and an actual final body-hash guard failure must restore the entire previous four-function/column/row state. Successful install/recovery must preserve existing business data, pending proposals/approvals, protected identities, other functions, RLS and ACL. A populated synthetic DOB remains after reverse recovery; retained-column reinstall must refuse rather than drop data. Exact-head native CI success is required before claiming these new cases verified.

## Recovery limit

`restore-unused.sql.review-only` is a saved, unexecuted recovery candidate, not a machine proof of zero use. Neither the frozen sources nor this composer add a usage ledger or a zero-use gate. Recovery intentionally retains the DOB column, dates, pending proposals, approvals and other original rows. A test that preserves a populated synthetic date proves mechanical retention only; it does not approve withdrawal after real use. Stop rollout and review actual usage, pending contracts, stored evidence and forward recovery before any later withdrawal. Because the retained column survives, the unmodified original installer cannot simply be rerun; that case fails closed and requires a separate compatibility review.

## Remaining stages

This is not a protected production backup/isolated restore, full current production schema check, actual GoTrue canonical save/approval proof, all-module atomic introduction, deployment/GRANT authorization, app distribution or iPhone confirmation. DOB has no new rollout flag, so publishing its contract itself requires an explicit separate introduction decision. Bank/document candidates and individual exemption remain OFF; their source is untouched. Existing original documents, signatures, payroll and bank records are outside this capsule's write scope.
