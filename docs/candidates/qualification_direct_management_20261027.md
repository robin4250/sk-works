# 管理者・サブ管理者による資格の直接管理候補

本人の写真申請は現状のまま保持する。社員資格書類では管理者・正規people権限を持つサブ管理者が、資格の追加・情報編集・削除をその場で行える。独立承認や別担当者の承認待ちは追加しない。

既存 `QualificationCloudPage` の登録フォーム・資格マスター・従業員選択を再利用する。新しいサーバー契約が利用可能なとき、登録は固定request ID付きの直接管理APIへ送信し、情報編集・削除のボタンを表示する。未導入・既定OFF・未知の能力応答は編集と削除を有効にしない。新方式で保存を試みた後に旧直接書き込みへfallbackしない。

権限は現在の同社 owner/admin/manager と `can_manage_people`、有効セッション・利用可能アカウントをサーバーが照合する。会社・操作者・対象・表示した全snapshotを結び付け、行ロックと固定IDによる再試行を使う。正式行の変更、元/変更後snapshot、操作ID・操作者・時刻の監査追加を単一トランザクションで行う。管理操作を本人専用申請のprepareへ流し込まない。

既存の正式資格履歴・写真履歴triggerを再利用する。情報編集は証明書番号・発行元・取得日・有効期限・備考のみで、写真を変えない。保存済み写真は既存の写真編集画面を再利用し、元からその資格に保存されているpathだけで並べ替え・一覧からの削除ができる。本人写真申請の承認は経由しない。資格削除後も元の正式行・管理監査・写真参照・実Storageオブジェクトを保持する。写真の新規追加・新しいファイルへの差し替えはこのAPIでは行わない。保存済み写真の整理だけを有効にする。本人の写真申請・承認の関数本体と初回本人登録INSERTを変更しない。

新監査は会社・従業員・Authの削除に巻き込まれないようcascade FKを持たない。プライバシー上の保持期限・消去手順、管理者の履歴表示は本番導入前に既存監査運用と照合する必要がある。監査はDB上のUPDATE/DELETEを拒否するが、DB所有者を含む絶対的な改ざん不能を意味しない。

旧PR #1493の独立承認案は保存済み試作であり、この直接管理方式には必須化しない。旧review-onlyの `guard_qualification_registered_update` が導入済みなら本候補は不明な迂回を行わず導入を拒否する。本番にはそのguardが存在しないことを読み取り確認した。

本番・main未変更、Release未作成。本番OFF導入・有効化・実GoTrue・実Storage bytes・iPhone操作の成功とは区別する。PGliteとNative PostgreSQL17のAuth/Storageは合成fixtureである。未使用復旧は操作履歴が0件で既定OFFのときだけ許可し、使用後は機能OFFで監査を保持する。

再試行のprivacy-v2補修は qualification_management_pending_privacy_20261027.sql.review-only と pending-privacy.md を参照。v1全文保存クライアントは有効化せず、v2で端末は不透明IDだけを保持する。実Cronの本文消去と正常実行を確認するまで新管理capabilityはOFF。未使用復旧は管理操作・準備・取消を一度も行っていない場合だけ許可する。
