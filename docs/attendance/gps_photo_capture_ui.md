# GPS + photo capture integration

The new path runs only when `get_attendance_capture_capability(company)` returns version 1, the same company ID and `capture_enabled: true`. Missing RPC, unknown version or a disabled gate keeps the existing path. This change does not enable any company or deploy a migration.

The camera, current GPS sample and storage upload are coordinated by `GpsPhotoCaptureController`. GPS failure, upload failure, camera failure and camera cancellation show a Confirm / Retake prompt. Confirm preserves the failure metadata and requested `location_photo` method; Retake starts a new camera capture and GPS acquisition. Company, source clock-in, site, route and driver vehicle stay in the captured context. Saving rejects changed company/selection rather than attaching a draft to a different shift.

`photo_observed_at` is when the camera returned. It is not shutter time. `photo_captured_at` is optional and comes only from the native metadata reader's known-offset EXIF / GPS UTC result. `gps_captured_at` comes from `Position.timestamp`. A sample more than 30 seconds from the known shutter time (or camera observation when shutter time is unavailable) is rejected. A capture address comes only from reverse geocoding that exact live sample. Unknown metadata stays NULL; site addresses and registration timestamps are not substituted.

Daily report evidence includes v1 rows with missing photos, shows failure status and missing-photo placeholders, and distinguishes unknown shutter time from server attendance registration time. Legacy NULL rows remain unchanged. The same generated PDF now includes evidence appendix pages containing available photos, exact saved coordinates and addresses, separate capture / attendance registration times, and explicit missing / failed evidence captions. A saved-photo download failure remains distinct from the persisted photo status. Preview, print and share use the same cached PDF bytes rather than a separate Flutter paper layout. The fingerprint includes evidence provenance and image bytes. Invoice and payroll report layouts are untouched.

Validation: ten pure controller tests cover success, GPS failure, stale coordinates, upload failure, cancellation, camera failure, retake, preserved source identity and unknown actual photo timestamps. Native metadata tests are inherited from the metadata dependency. No Flutter / Dart SDK is available locally; CI and actual iPhone camera / location / offline checks remain required. A staged-path insertion error keeps the uploaded object because a network error cannot prove the server rolled back; it does not delete potentially committed evidence. Orphan cleanup requires separate reconciliation. There is no durable upload retry outbox in this change. A failed upload remains visibly failed.

PDF validation adds a synthetic PNG, one missing upload, one unavailable saved photo and explicit known / unknown capture timestamps. CI produces an actual Flutter PDF and renders all four pages with PyMuPDF for visual review; this does not replace real iPhone testing.
