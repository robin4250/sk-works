Appleはアカウント作成を提供するアプリについてアプリ内から削除を開始できる経路を求める。
会社の給与・承認履歴を削除ボタンで一括消去する設計にはせず、本人アカウントの削除と
会社が保持すべき記録を区別する。保持の必要性・期間は運営方針として確定させ、
ログアウトや単なる退会申請だけで要件達成と断定しない。[公式の削除要件](https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion)

保存基盤の範囲と再検証方法は [削除基盤ソース保存](recovery/account_deletion_source_20261008/README.md) を参照。入口のモック試験成功は、本人UI・実削除・保持分類・外部資格情報失効・完了通知の通し確認と区別する。

## 実装に基づく収集データ棚卸し

以下はApp Store Connect回答の下書き材料であり、申告済みラベルではない。
Supabaseへの保存は端末外での収集に当たる。本人と結び付く業務データは原則として
「ユーザーに関連付けられる」前提で確認する。機能をOFFにできることだけを理由に
「収集なし」としない。[Appleの分類と回答方法](https://developer.apple.com/app-store/app-privacy-details/)

| 実際の機能・保存先の根拠 | データ | Apple分類の候補 | 目的・確認点 |
|---|---|---|---|
| `profile_repository.dart`、社員登録・個人情報 | 氏名、電話、メール、住所、社員ID、所属・職種・入社日、緊急連絡先 | Contact Info / User ID / Other User Content | アカウント・社員管理。任意項目を含む実際の保存範囲を確認 |
| 個別給与設定・給与明細・振込先 | 給与額、控除額、銀行口座 | Other Financial Info / Payment Info | 給与計算・支払帳票。アプリ内課金の有無とは別の申告対象 |
| `gps_auto_attendance_service.dart`、勤怠 | 緯度経度、現場、出退勤日時、勤務実績 | Precise Location / Other User Content | 出勤確認。位置精度と背景保存の実際の挙動を確認 |
| 資格・社員書類・会社提出書類 | 資格証、添付PDF、本人確認等の写真、任意書類 | Photos or Videos / Other User Content、内容によりSensitive Info等 | 書類の内容で分類が変わる。健康関連書類を受け付ける場合はHealth等も別途評価 |
| チャット・友達・グループ | メッセージ本文、写真、参加者 | Emails or Text Messages / Photos or Videos / Contactsの適用要確認 | 業務連絡。端末の電話帳を読み込む実装は今回確認していない |
| `usage_analytics_repository.dart` → `record_usage_event` | 操作イベント・画面/機能キー | Product Interaction | 内部の利用状況分析。集計表示だけでもイベント収集の有無は別に申告 |
| Supabase認証・Storage・ネットワーク/SDK | 認証ID、アクセス記録、SDK側で扱うデータ | User ID、Diagnostics等は実際の保持内容に応じて判断 | 委託先・SDKの仕様と公開候補の通信を確認。診断収集なしと未検証で断定しない |

Face IDは `local_auth` による端末認証であり、顔画像・Face IDテンプレートをサーバーへ
収集する実装は今回確認していない。生体認証を使うだけで生体データ収集と決め付けない。
広告SDKやATT要求の実装も今回確認していないが、「追跡なし」の最終回答はSDK・通信・
委託先を含めた確認後に行う。自社の利用分析と他社広告向け追跡は区別する。

## 審査操作ガイドの準備

資格情報はGitHubへ保存しない。審査専用の架空会社・社員データを使用し、実在会社の
給与・銀行口座・位置履歴にアクセスできる審査アカウントを作らない。

1. 管理者用と一般社員用のアクセス方法を、App Review Informationへ安全に記載する。
   初回QR、追加パスワード、会社権限などを審査員が再現できる手順にする。
2. 会社データ、社員データ、勤怠、給与明細、請求書、支払証明書の主要経路を案内する。
   登録だけで出勤なしでも支払証明書をプレビューできる経路を含める。
3. 背景位置情報はGPS自動出勤を本人が有効化した場合の使用として説明する。
   手動出勤、位置情報拒否時の動作、停止操作も案内する。
4. アカウント削除の開始から完了、給与の閲覧権限、帳票共有の動作を審査用データで確認する。
5. 審査期間中のバックエンド稼働と連絡窓口を確保する。審査で使えない一時コードに依存しない。

アクセス情報や特殊な操作を審査情報に記載することはAppleの案内に沿う。
[App Review](https://developer.apple.com/app-store/review/)

## 登録完了後に行うこと

- Apple Developer Program会社登録の有効化、契約、チーム・App Store Connect権限を実際に確認する。
- 同じBundle IDでアプリレコード・配布署名・プロファイルを確認し、既存ビルド番号と重複しない候補を作る。
- CI・実機・既存TestFlightゲートを通過した候補をアップロードし、社内試験から始める。
- 実際のプライバシー回答、公開ポリシーURL、審査情報、掲載素材、配信地域等を登録する。
- 公開要件と試験が揃った後に審査へ提出する。公開日は審査結果を見て管理し、登録待ちの段階で約束しない。

現時点で未完了：アカウント削除の利用者経路の通し確認、公開プライバシーポリシー、
SDK/通信を含む最終収集ラベル、審査専用アクセス、掲載スクリーンショット、Apple側の
登録・署名・アップロード・審査・公開。これらを帳票CI成功だけで完了扱いにしない。

実Release成果物の読み取り監査手順は [RELEASE_PRIVACY_ARTIFACT_AUDIT.md](RELEASE_PRIVACY_ARTIFACT_AUDIT.md) を参照。架空成果物でのスクリプト検証と、実Macでの署名・Release・SDK宣言確認は区別する。
