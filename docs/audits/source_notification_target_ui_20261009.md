# Source notification target UI (staged)

Only `group_report_saved` and `vehicle_driver_started` call recipient-only `get_source_notification_target(notification_id)`. Its returned company, event key, original report/source ID and exact work date must match the stored notification before opening. The dedicated read-only page queries exactly that ID and company under existing RLS and validates the persisted work date again. No date/site first-result inference or current-month default is used.

Legacy notification routes remain unchanged. RPC unavailable, inaccessible target, missing row, session change or inconsistent work date displays an unavailable state; it does not open a substitute month/report or grant access. The existing notification read timestamp remains separate from report signature/approval state. The page has no business completion mutation, broad vehicle manager page, salary fields or permission grants.

This is the initial read-only recipient destination, not a new report approval workflow. Report information includes saved work description, site and roster. Vehicle-start information includes driver, vehicle and clock-in time; it does not expose vehicle manager records. Existing photo/address proof presentation, intermediate-photo capture, administrative vehicle assignee settings and external maintenance email transport remain separate unfinished work. Production notification rollout remains OFF; server final-save publication still requires integration. Flutter tests must run in CI; no local Flutter SDK or physical iPhone verification is available here.
