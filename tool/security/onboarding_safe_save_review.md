# Review-only atomic onboarding photo omission RPC

No production apply, migration, client modification, Auth configuration, RLS change, notification delivery, or real user data access. Child of #1143; that head is unchanged. Only two new RPC functions are proposed.

## Failure this addresses
A client can read photo_upload_allowed=false, then an operator restores the previous save RPC before the client submits NULL image paths. Atomic deployment alone does not prevent this in-flight rollback race. The new client must use ONLY save_employee_onboarding_profile_without_photos (seven existing text inputs) for omission, never fall back to old save with NULL photographs when this RPC is missing or errors.

## Transaction and permissions
The private SECURITY DEFINER implementation uses empty search_path, auth.uid(), current account restriction, and a STRICT own eligible-invite SELECT FOR UPDATE. No target user/invite argument is accepted. No eligible or ambiguous eligible invites are denied before writes. The row lock serializes existing-row changes with the snapshot, and is held until request commit/rollback. Snapshot contains only required identity fields and three photo references, entirely inside the server. Existing save logic is invoked once with its original seven text parameters plus three NULLs; text validation, status and notification source remain centralized there. An IS DISTINCT FROM assertion verifies ID/company/user and all three references after the save. Any mismatch raises a generic 55000, aborting that request and its transactional notification writes. No path appears in return values, errors or logs. External notification side effects outside the database transaction are not proven by the synthetic sink.

Public wrapper is SECURITY INVOKER. Both functions explicitly revoke PUBLIC/anon/service_role and grant authenticated EXECUTE only. No table/column grants, auth.sessions access, admin role changes, old function replacements or public-schema definer are introduced. Existing private schema usage is a deployment prerequisite inherited from #1143. Default EXECUTE exposure is closed in the same transaction. Removing either new function during rollback produces failure, not permission to call the old NULL API.

## Synthetic verification
The dedicated SQL fixture uses the exact captured old save from onboarding_storage_catalog.json and #1143 retained save, not a second business implementation. It verifies old-save rollback rejection, all original data and synthetic notifications unchanged on failure, NULL new applicants, retained legacy references, anonymous/uninvited/restricted/ambiguous rejection, missing API failure, no extra PII grants, and exact original source/OID/ACL/data/company-owner restoration. Local PGlite: 14 checks passed.

The isolated Actions fixture pins CLI 2.121.0 in a private temporary directory with an empty local stack, real synthetic GoTrue identities, actual Data API account pre-hook, no production credentials, and no Storage. It additionally tests actual HTTP stale-capability/original-save rollback and two concurrent PostgreSQL connections: hold a row lock with a new synthetic photo reference, observe Data API waiting, commit the holder, verify the RPC preserves the new reference. Runtime results must be read from this PR CI; code alone is not a pass. Missing API is checked as PGRST202. There is no client code in this PR and therefore no claim of client fallback handling or photo-upload completion.

## Limits and deployment gate
This API preserves already existing references and permits text-only submissions while the current beta pause remains. It does not reopen image upload, revoke signed URLs, change Storage policies, prove Apple/Google E2E, or prove production notification delivery. Function replacement by a privileged actor with arbitrary side effects is outside the invariants this wrapper can contain; production must deploy only reviewed SQL. Client integration is a separate PR after exact backend contract verification. Production changes require protected backup, tested restore, administrator identity/access preservation and explicit final user approval.
