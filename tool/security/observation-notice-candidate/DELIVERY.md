# Isolated authenticated-observation delivery candidate

This draft connects an already authenticated collector evidence insert to a durable, private outbox in the same transaction. Enabled configuration pins collector, company, Master recipient and revision from administrator-controlled storage, never from event bytes. Publishing an event is service-authorized and locks its row, revalidates the current Master/company role, configuration and existing HMAC evidence, then atomically records a private in-app inbox item and audit. Repeated publication returns the existing state. No IP, request body, token, correlation key or personal data is copied into the inbox.

This is not deployed and defaults OFF. During OFF, collector events deliberately do not create notice entries: no claim of monitoring coverage or replay/backfill is made. Any held state needs a separately audited recovery design. A candidate public read function is restricted to authenticated callers and checks a live session, current Master/company role, and the existing one-use collector-read proof. Publication has an explicit POST-only, service-role-only wrapper but is unscheduled, default OFF, and cannot choose a recipient. A candidate UI and explicit read/review actions use current Master identity, session, collector-specific proof, immutable command id and versioned state. They are not installed or connected to a live deployment. No hosted service configuration, independent audit anchor, retention or real-host recovery is connected. Worker-side outbox retries are separate and already tested. Before enabling, verify Master-session+operation-proof gated listing against actual GoTrue and test read/review with real proof and concurrent CAS, test race-safe Master revocation and config changes, backlog/backfill and fail-safe coverage, bounds/retention, catalog/body pinning and safe unused restore. Run actual collector SQL, genuine GoTrue and Postgres concurrency tests, then real host/notification/iPhone tests. A failed or unknown acknowledgement must not duplicate records or erase evidence. No production data, keys or actual notifications are used.

Native CI candidate uses the exact existing collector/proof SQL with PostgreSQL 17 and real pgcrypto against synthetic local identities and keys. Two connections race the same signed ingest and notice publication. This is not a real GoTrue, hosted Collector, push delivery or production test; consult the actual CI result before claiming success.

A separate disposable GoTrue/Edge/PostgREST CI fixture reuses the exact pinned existing Collector test setup and tests this notice reader with actual user JWT, real proof issuance, separate-user denial and revoked session. It provisions synthetic local keys and data only. The generated fixture source was syntax checked locally; actual GoTrue CI outcome must be checked separately.

See OPERATIONS.md: the existing 7-day collector purge makes this candidate unsafe to deploy until atomic, independently anchored retention and safe recovery are implemented and verified.
